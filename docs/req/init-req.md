# 课题目标回顾：融合官方文档与开源源码挖掘的 API 知识库系统

## 课题目标

构建一套**融合官方文档 + 海量开源源码挖掘**的 API 知识库系统：

- **底层**：代码挖掘与知识构建
- **中间层**：知识库 + 检索引擎
- **上层**：**Web 人机查询界面 + MCP 工具服务双出口**

系统需支持多版本 API、知识条目可溯源、人工审核冲突、外部 AI 助手令牌鉴权，解决大模型 API 幻觉（不存在方法、废弃接口、版本错误、调用顺序错误）。

---

## 一、核心对标项目：官方文档抓取 + 版本索引 + MCP 服务 + WebUI（最高优先级）

### Grounded Docs（docs-mcp-server）

- **仓库地址**：https://github.com/arabold/docs-mcp-server
- **许可证**：MIT，TypeScript
- **项目定位**：开源版 Context7 服务端，完整实现库文档爬取、版本化索引、检索、MCP 服务、Web 管理界面。

#### 项目能力

1. **文档采集**：遍历库文档 sitemap，抓取 PyPI/npm 等第三方库官方文档，HTML 清洗、分块转 Markdown；支持增量抓取，遵守 robots。
2. **版本隔离**：同一库不同版本文档独立索引，解决 API 废弃、版本不一致问题。
3. **检索引擎**：SQLite 实现全文 FTS + 向量检索，支持本地 Embedding。
4. **双出口架构**：
   - **Web 界面**：人工提交抓取任务、检索文档、查看索引；
   - **MCP Server**：提供 `search_docs`、`get_section` 工具，支持 stdio/SSE 两种传输，可增加令牌鉴权。

#### 可借鉴内容

1. 版本化文档数据模型、库/版本/文档块的表结构设计；
2. 文档站点爬虫策略、页面分块策略（按标题层级切分，保留文档上下文）；
3. 同一索引同时对外提供 Web 查询和 MCP 工具调用的双出口架构；
4. MCP 工具定义、参数设计、SSE/stdio 两种 MCP 传输实现思路；
5. 后台异步抓取任务队列、任务状态管理。

#### 局限性（课题创新点来源）

仅采集**官方静态文档**，**不解析开源代码，无法挖掘真实工程里 API 调用序列、调用先后顺序、参数共现频次**；无知识库人工审核、冲突条目处理工作流。

#### 论文定位

Grounded Docs 作为 Context7 的开源替代，实现了第三方库官方文档抓取、多版本索引，并提供 Web 界面与 MCP 工具双出口，能够缓解大模型在 API 文档层面的幻觉。但其数据源仅局限于官方文档，无法获取真实工程中的 API 调用顺序、参数使用习惯等统计层面的使用模式。

## 二、源码知识抽取项目：AST 解析、API 调用提取、代码知识图谱

### Graphify

- **仓库地址**：https://github.com/Graphify-Labs/graphify
- **许可证**：Apache2.0，Python + tree-sitter
- **项目定位**：基于 tree-sitter 多语言语法解析，把源码转为代码知识图谱。

#### 项目能力

1. tree-sitter 解析 Java/Python 源码 AST，提取类、函数、导入关系、API 调用边；
2. 构建代码实体知识图，节点为 API/类，边代表调用、继承关系；
3. 可导出图结构，支持增量仓库解析。

#### 可借鉴内容

1. tree-sitter 的 AST 解析流水线，从源码中抽取 API 调用实例；
2. 代码实体建模方式，API 节点、调用关系、源码位置（文件 + 行号）的存储；
3. 批量解析开源仓库、增量索引的实现思路。

#### 局限性

仅生成静态调用图，**不做跨项目频繁 API 调用序列挖掘，不统计调用频次**；不包含文档抓取模块，没有 MCP 服务和 Web 查询界面。

#### 论文定位

Graphify 利用 tree-sitter 构建代码知识图谱，可提取源码中的 API 调用关系，但仅保留静态结构，缺少跨项目的 API 调用序列挖掘与频次统计能力。

### DeepWiki

- **仓库地址**：https://github.com/deepwiki-open/deepwiki
- **许可证**：MIT
- **项目定位**：源码驱动自动生成结构化 Wiki 文档。

#### 项目能力

1. 克隆源码仓库，AST 解析提取 API/类定义；
2. 自动生成 Wiki 页面，**每一条知识条目绑定源码行号，支持溯源**；
3. 生成 VitePress 结构化文档目录，支持 MCP 读取生成后的 Wiki 内容。

#### 可借鉴内容【重点：溯源机制】

知识条目**来源证据绑定机制**：每条 API 知识必须附带来源（文档 URL 或源码文件 + 行号），保证 AI 返回结果可核查；知识库分层目录组织。

> **注意**：**不要借鉴其 LLM 生成 wiki 摘要的逻辑**，你的课题是直接存储原始文档片段与源码挖掘的调用实例，避免引入 LLM 二次生成带来的幻觉。

#### 局限性

不是外部官方文档爬虫；Wiki 内容依赖 LLM 摘要生成，并非原始文档；不做跨仓库大规模 API 调用序列挖掘。

#### 论文定位

DeepWiki 实现源码驱动的可溯源 Wiki 文档，所有知识均可回溯至源码位置，保障推荐依据可核查；但 Wiki 内容依赖大模型生成，不采集外部官方文档，也不挖掘跨项目的频繁 API 调用序列。

## 三、EpiCoder

- **仓库地址**：https://github.com/microsoft/EpiCoder
- **论文**：EpiCoder: Encompassing Diversity and Complexity in Code Generation（ICML2025）
- **许可证**：MIT
- **项目定位**：**代码指令数据合成框架**，基于 Feature Tree 特征树，从原始代码中提取分层语义特征，用于构造训练数据、微调代码大模型。

### 项目能力

1. 输入海量原始代码片段，做 AST 基础上的**语义特征提取**，构建 Feature Tree（特征树，和 AST 不同：AST 是语法树，Feature Tree 是代码语义特征树）；
2. 提取 API 名称、类型、参数、控制流、调用上下文；对代码特征聚类、统计特征出现频次；
3. 基于特征树采样，生成大量高质量代码指令微调数据；
4. 附带完整数据处理 pipeline，包含代码过滤、特征抽取、统计模块。

### ✅ 对你课题的可借鉴内容

1. **API 特征抽取流水线**：怎么从原始代码片段中提取 API 调用、参数类型、上下文特征；
2. **Feature Tree 分层建模思路**：不只是扁平的 API 列表，把 API、参数、类型、调用上下文组织成层次化特征；
3. **频次统计、特征聚类**：统计不同 API、API 组合的出现频率；这正好用于你挖掘层的 API 共现统计；
4. 代码样本清洗、过滤坏样本的工程逻辑（过滤残缺代码、测试文件、自动生成代码）。

### ⚠️ 局限性

1. 目标是**生成 LLM 训练指令数据**，**不是检索知识库**；没有检索引擎，没有 Web 查询界面；
2. **没有 MCP 服务**，不能给 AI 编码助手提供工具调用；
3. 不做频繁序列挖掘（PrefixSpan/GSP）；EpiCoder 的特征树偏向单片段代码语义，**不跨代码片段挖掘"API 调用先后序列模式"**；
4. 没有官方文档抓取模块；没有知识库人工审核、冲突处理流程。

### 论文相关工作表述

EpiCoder 提供完整开源的代码特征抽取框架，提出 Feature Tree 分层语义特征建模方法，能够从原始代码中提取 API、参数、控制流等特征并完成频次统计，用于合成代码大模型训练数据。但其系统目标面向训练数据生成，**不构建检索知识库，缺少 API 调用序列挖掘能力，也没有 MCP 服务和面向开发者的 Web 查询入口**。

   - 仓库：https://github.com/unclecode/crawl4ai

## 五、更新后的【相关工作】段落

现有 MCP 文档检索系统如 Grounded Docs，作为 Context7 的开源替代，实现第三方库官方文档抓取、多版本索引，并提供 Web 管理界面与 MCP 工具双出口，能够缓解大模型在 API 文档层面的幻觉。但其数据源仅局限于官方文档，无法获取真实工程中的 API 调用顺序、参数使用习惯等统计层面的使用模式。

DeepWiki 提出源码驱动的可溯源 Wiki 文档方案，所有知识条目均可回溯至源码行号，保障推荐依据可核查；但 Wiki 内容依赖大模型生成，不采集外部官方文档，也不挖掘跨项目的频繁 API 调用序列。Graphify 基于 tree-sitter 构建代码知识图谱，可提取源码中的 API 调用关系，但仅保留静态结构，缺少跨项目的 API 调用序列挖掘与频次统计能力。

EpiCoder 提供完整开源的代码特征抽取框架，提出 Feature Tree 分层语义特征建模方法，能够从原始代码中提取 API、参数、控制流等特征并完成频次统计，用于合成代码大模型训练数据。但其系统目标面向训练数据生成，不构建检索知识库，缺少 API 调用序列挖掘能力，也没有 MCP 服务和面向开发者的 Web 查询入口。APP-Miner 等传统 API 挖掘方法可从海量源码挖掘 API 调用序列模式，但缺少标准化 MCP 工具接口，无法直接为 AI 编码助手提供服务，也缺少面向开发者的 Web 查询入口。

**本文创新点**：融合两路数据源（① 开源库官方文档；② 海量开源代码库静态挖掘得到的 API 调用序列、频次模式）构建统一知识库；知识库条目附带来源证据，支持人工审核冲突；同时提供 Web 查询界面和 MCP 工具服务，人机共享同一套知识库，兼顾文档规范与真实工程实践，解决大模型 API 方法签名、版本、调用顺序幻觉。

## 七、系统三层架构简述

### 1. 底层：代码库挖掘与知识构建层

- **分支 A（文档挖掘）**：爬虫抓取 Python/Java 库官方文档，清洗、分块、绑定版本、记录文档来源 URL；
- **分支 B（源码挖掘）**：拉取开源仓库，tree-sitter 做 AST 解析；参考 EpiCoder 做 API、参数、上下文特征抽取与频次统计；使用 PrefixSpan 挖掘频繁调用序列，绑定源码文件 + 行号溯源信息。

### 2. 中间层：知识库与检索引擎

- **数据库存储**：库版本元数据、文档条目、API 调用序列、来源溯源、审核状态；
- **检索**：BM25 全文检索 + 向量检索 + 特征重排（结合调用频次做重排）。

### 3. 上层：双出口服务

- **Web 界面**：开发者查询 API、提交反馈；知识库管理员审核条目、处理冲突；系统管理员配置采集任务；
- **MCP 工具服务**：令牌鉴权，供外部 AI 编码助手调用，返回结构化 API 知识。

> 两条出口共享同一知识库，保证人机查询结果一致。
