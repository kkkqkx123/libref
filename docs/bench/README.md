# 检索基准

本目录记录检索问答基准的设计与运行约定。脚本与数据落在 `tests/e2e/bench/`，
设计依据见 `design.md`。

## 目标

基准只回答三个问题：检索链路相对真实 BM25 基线是否值得，融合聚合方式选哪一个，
多语言与不同复杂度工程上这些结论是否还成立。回答这三个问题的前提是**语料稳定**：
语料一变，历史数字与门禁下限全部失效。

## 三层边界

| 层 | 位置 | 生命周期 | 读它的东西 |
|---|---|---|---|
| 获取层 | 临时目录 | 一次运行，导出后丢弃 | 无 |
| 归档层 | `tests/e2e/bench/fixtures/{项目}/{分支}/` | 不可变，只在显式重新获取时替换 | 构建、评测、扫描 |
| 派生层 | `tests/e2e/bench/data/`、`outputs/` | 每次运行重建，不入库 | 只有人 |

获取层保留生产存储的命名与配额逻辑，因为要验证的正是生产获取链；归档层不保留任何生产
命名，身份写在元数据里，路径只表达"哪个项目、哪条分支"。

## 归档

一份归档是一个目录，包含一个载荷与一份元数据：

- 文档分支载荷是原始正文的压缩行文件（不是净化文本），因此净化与分块的改动可以在相同输入上比较。
- 源码分支载荷是固定提交的工作树打包，不含版本库目录；提交标识记在元数据里。
- 元数据记录身份、配方、获取时间、载荷摘要、内容摘要（页集合或源码树）、修订。

修订是载荷摘要的前 12 位，不设人工标签，所以无法与内容脱节。归档写入后置为只读；
构建时先校验身份与载荷摘要，消费过程中再校验内容摘要，不一致即失败。归档被改动、
规格被改动但没有重新获取，都会在这一步暴露。

## 门禁

门禁按夹具标识分条，不做默认回退，并绑定归档修订：数据集修订与门禁记录的修订不一致即失败。
重新获取视为新语料，下限必须重新测量，不能沿用。全文本单路在两种运行模式下都进下限；
融合与精排只在真实模型下进下限，因为离线替身的质量反映替身而不是检索设计。

## 运行

获取只做一次：

```bash
uv run python -m tests.e2e.bench.fetch                 # 一次获取，产出不可变归档
uv run python -m tests.e2e.bench.fetch --only httpx/docs --reacquire   # 重新获取，产生新修订
```

之后全部离线：

```bash
uv run python -m tests.e2e.bench.build                 # 归档 → data/bench.db + manifest.json
uv run python -m tests.e2e.bench.evaluate [--real]     # 方法矩阵、探针与门禁
uv run python -m tests.e2e.bench.sweep [--real]        # 参数扫描
LIBREF_RUN_BENCH=1 uv run pytest tests/integration/test_retrieval_bench.py -q
```

## 加一个项目分支

1. 在 `bench.json` 加一条：项目、分支、身份、获取配方。
2. 跑 `fetch.py` 获取并冻结归档；读它输出的语料报告（页数、块数、语言、实体、调用、挖掘规模），
   确认语料可用。
3. 在已建库的数据集上起草判定集，锚点用身份（标题路径、限定符号、文件相对路径），不用行号。
4. 冻结判定集与门禁：按实测值减噪声带设下限，把修订写进 `gates.json`。
