# 检索基准设计：语料覆盖、聚合与回归口径

目标函数是让基准能回答三个问题：多语言、不同复杂度工程上还成不成立；融合聚合方式相对
真实 BM25 到底赚不赚；语料本身是否稳定到可以让门禁长期有效。操作与目录约定见同目录的
`README.md`，本文记录取舍依据与后续扩展方向。

## 一、盲区

语料已有四个库的八条分支：`httpx`（Python）、`zod`（TypeScript）、`jsoup`（Java）、
`fiber`（Go），每个库都是官方文档站加固定发布标签的官方仓库。文档分支 15–65 页 / 177–4723 块，
源码分支 23–220 文件 / 739–8405 实体 / 1558–12158 调用；整套数据集重建约 190s，
方法矩阵评测约 16s。判定集 377 条，按 `qualified` / `semantic` / `cjk` / `absent` 分类，
每条带 `query_lang` 与可选全局作用域（含 16 条跨库全局查询），每个新夹具每类不少于 8 条。
扫描共 24 个检索期变体加 6 个分块变体，每个变体单独调一格参数。
夹具的获取、冻结与路径形态已按第七、八节改造完成，下面列的是仍然存在的度量盲区。

已实测出的关键信息，直接决定后续设计：

- 同一默认配置在方法矩阵里读到文档融合 MRR 0.762，在扫描里读到 0.798；`rrf_k=10` 与 `k=20`
  在源码上差 0.022。一条查询的换位就值 0.07 召回 / 0.02～0.07 MRR，噪声与信号同量级。
- 打分尺度跨三个数量级：全文单路 4.2～33.5，融合 0.03～0.095，精排 0.0001～0.995。
  当前融合只取排名，原始分被丢弃，因此任何"按分聚合"的方案既无法评测，也无法与现有实现比较。
- 离线替身（哈希词频伪向量 + 词覆盖重排）与 BM25 的排序高度同源，融合在替身下几乎无损，
  所以替身数据不能用来判断聚合方式；聚合结论只能在真实模型下产生。
- 挖掘加权（`freq_alpha` / `cluster_alpha`）以乘法叠加在聚合分之上，同一个系数在
  融合分（约 0.08）、精排分（约 0.15）、全文分（约 10）上代表完全不同的权重，
  这是聚合方式与加权形式耦合的直接证据。
- 现有"全文单路"是生产权重的一次运行，不是基线：它没有分泳道观察、没有同池深度对照、
  没有与自身变体（查询整形、池深、列权重）的相对位置，也没有置信区间。

盲区按影响排序：

1. 语言覆盖已到 Python / TypeScript / Java / Go 四种（`httpx`、`zod`、`jsoup`、`fiber`），
   缺口在 Rust、C# 与 Kotlin/Groovy：宏、表达式树与跨语言混排三种形态仍无代表。
2. 复杂度仍只有中库一档：缺小库、多模块大仓、跨语言仓、含生成代码的仓。
3. 文档语料全英文；中文查询（每夹具 9–12 条）在英文语料上确定性失败，
   降级机制（`cross_lingual` 标记、全文路不计入召回失败、真实模型下限位）已就位，
   CJK 文档站与"英文查询打中文语料"这半边随波次二落地。
4. `absent` 的空结果率仍在 0～0.5 之间（空结果不是检索器该追求的行为），因此"无答案"改由
   证据充分度判定回答：弃答率现在 0.5～1.0，误弃答率 0～0.17，两项都在门禁里。
5. 缺单路基线：没有"仅全文"与"仅向量"的左右对照，融合增益无法归因。
6. 统计口径已建立：判定集分 `dev`/`test`，报告给按查询重采样的 95% 区间，
   扫描表给配对差值及其区间。分辨率仍受判定集规模限制：小夹具的区间宽到 ±0.09，
   `fts_weights` 四档的移动仍全部落在区间内（"不显著"），这不是缺方法而是缺查询数。
7. 池级诊断已建立：全部夹具的 fused 行都按"命中 / 聚合丢分 / 召回丢分"三分，
   八个夹具上聚合与召回两类丢分均非零；首位保留探针仍只跑首个文档夹具。
8. 探针只跑在每类语料的首个夹具（文档类：材料预算、置信度、查询整形、首位保留；
   源码类：副表加载成本），其余夹具只有方法矩阵与分类型指标。

第 3 条的降级机制、第 4、6、7 条已按 `docs/plan/bench-remaining-gaps.md` 落地：分级相关（目标节 2 分、
目标页 1 分）、dev/test 分栏、配对重采样区间与最小可检出差异、无答案的空结果率与弃答率两分栏、
检索侧的证据充分度判定、跨语言方向分栏与全文路降级、池级三分，以及波次前置（夹具分级、
全局作用域、路径前缀断言、成本预算、`.gradle` 后缀）。仍未落地的是第 1、2 条的项目、
第 3 条的中文语料侧与真实模型跨语言下限、第 5 条单路基线，与波次二至四的项目。

## 二、语料覆盖：多语言与不同复杂度

### 夹具规格

`bench.json` 是夹具列表，每条声明项目、分支（文档/源码）、身份（库、生态、版本）与获取配方；
夹具标识由"项目/分支"推出，不单独存一份以免两处漂移。已按夹具标识全面去硬编码：

- 获取层不写夹具树：抓取与克隆落在临时目录，导出成归档后才丢弃，因此生产存储的命名层级
  （生态/库/版本）不再出现在夹具路径里，也不会与规格里的生态不一致。默认分支的检出走生产仓库
  管理器；声明了 `ref` 的夹具在获取层浅克隆并检出该 ref，因为它要的不是分支头而是固定发布，
  属于另一种获取方式而不是同一件事的两套实现。解析到的提交写进元数据，标签被上游强推时载荷
  摘要随之变化，门禁绑定修订即失败。
- 源码归档只打包被索引的子树，条目保留仓库相对路径：档案体积与被索引范围一致，
  源码地址与"索引整仓"时完全相同，大仓不必为了索引一个子目录而打进整棵检出。
- 源码分支声明可选的 `ref`（发布标签）：未声明时跟随默认分支，标签固定为 `head`。目录名与
  夹具标识都带上这个标签（`fixtures/{项目}/code-head`、`code-v1.2.3`），所以列出夹具目录就能
  看出哪些载荷是分支头、哪些是固定发布；源码分支的版本（数据集作用域、`repo://` 地址前缀、
  判定集与门禁的键）由该标签推导，规格里写死 `version` 会被拒绝。
- 构建清单按夹具标识记录，含归档修订、载荷摘要、提交、页数、泳道块数、实体与调用、挖掘规模；
  作用域与源码地址前缀都从清单推导（源码地址形如 `repo://生态/库/版本/相对路径`）。
- 判定集与门禁按夹具标识取键，缺条即失败，不做默认回退；门禁额外绑定归档修订。
- 每夹具带体检断言：文档分支页数与块数非零；源码分支的 `languages` 必须声明，且语言分布、
  文件全解析（解析数等于文件数）、实体、调用、源码块任一不满足即构建失败，避免语法缺失导致的
  "静默零产出"被当成绿色基准。
- 文档分支必须声明 `doc_version`，获取时从"页面路径段 → canonical → 版本元数据"取证并比对，
  不一致即失败；站点什么都不声明时记 `unversioned`。文档与源码的版本证据因此都来自观测而不是
  标签，报告在同一行并列"文档版本（信号）"与源码提交。
- 判定目标在评测前对齐语料：指向数据集从未收到的页面或源码路径时直接失败，与召回损失分开。
- 文档配方支持路径前缀限定（`path_prefixes`），用于同一页有多个版本路径的站点。
- 仍需补齐：判定集的相关等级、调参/门禁划分与跨分支查询类型。

### 语言矩阵

覆盖九种受支持语言的全部不现实，按"提取机制差异"而不是"语言数量"选取，每类至少一个：

| 机制 | 代表语言 | 覆盖要点 | 状态 |
|---|---|---|---|
| 相对导入 + 装饰器 + 异步 | Python | 跨文件相对导入与装饰器 | `httpx` |
| 路径别名 + 桶文件重导出 | TypeScript / JavaScript | 跨文件别名两遍解析最容易被击穿的形态 | `zod` |
| 泛型 + 重载 + 内部类 + 注解 | Java / C# | 符号式查询的限定名形态 | `jsoup`（C# 缺） |
| 宏 + 属性 + 模块可见性 | Rust | 声明与调用的文本形态差异 | 缺 |
| 接口嵌入 + 包级命名 | Go | 同名方法跨包消歧 | `fiber` |
| 扩展函数 + Gradle 多语言混排 | Kotlin / Groovy | 同一仓库内多语言分组与挖掘 | 缺 |

跨语言仓（Java + Kotlin、小程序里的 Python + JS）单列一档，用来验证分组与挖掘不串语言。

### 复杂度档位

规模决定"召回是否够得着"，也决定挖掘副表成本是否有意义，按三档设计：

- 小库：单包、数千行，判分集小而精确，用来固定语言级回归下限，构建成本最低。
- 中库：多包、数万行，与现有 httpx 同级，主判定集所在。
- 大仓：多模块单仓十万行以上，含生成代码、示例目录与多语言混排；用子目录与固定标签
  限制索引范围，只要求"不退化"，不追求满分，同时采集构建耗时与内存作为独立门禁量。

每档都记录构建耗时、块数、挖掘副表规模，使"检索质量"与"索引成本"在同一张表里可比。

### 文档语料

英文文档站已有三个，"围栏与表格密集 + 站内锚点跳转"由 `zod` 补上（单页锚点跳转、
表格与围栏交替），"llms.txt 优先于 sitemap"也由它补上（站点没有 sitemap）。
仍缺一个 CJK 文档站（中文或中日混排），用来验证分词器、词干化与 CJK 展开在真实页面上的行为，
并把"英文查询打中文语料"这半边补上——"中文查询打英文语料"已由现有夹具的 `cjk` 类型覆盖，
实测在全文单路上召回接近零。

### 判定集规模与构成

当前每条查询值 0.07 召回，无法支撑任何细粒度比较。每个夹具的判定集要求：

- 有答案查询不少于 40 条，每个类型不少于 8 条；当前 320 条（含无答案），八个夹具各 40–50 条。
- 类型扩为：符号式、语义式、查询语言≠语料语言、标识符形态（下划线/驼峰/短横线/帕斯卡）、
  报错文本、跨库同名消歧、多版本作用域、无答案。
- 每条查询带 dev/test 划分：调参只用 dev，门禁只读 test，报告两栏并列。
- 挖掘加权需要专门的判定集：查询只命中一个 API，而正确答案要靠共现/序列模式把页面顶上来；
  现有四档参数零差异说明这类查询完全缺失。

### 成本控制

按"快档 / 全档"两级运行：快档只在离线替身下跑小库夹具与不变量，用于提交前自检；
全档在真实模型下跑全部夹具与统计口径，作为发版与调参依据。分块扫描只在大仓以外的
最小夹具上重建数据集，避免每次重建整仓。

## 三、综合调参

现有扫描是单格轮换（一次只动一个旋钮，其余固定），缺少目标函数、缺交互、缺显著性，
产生的表格还要人工抄成结论。需要改成可判定的调参流程：

- **目标与约束**：主指标定为 test 划分上的 nDCG@5，召回设下限，成本设上限（每查询延迟）。
  约束不满足的方案直接淘汰，不做加权折中。
- **交互分组**：按耦合关系分块做坐标下降，每块二到三档，块内联合变、块间轮流。
  必设的块：分块预算 × 泳道；池深（召回倍数与候选下限）× 精排深度 × 截断；
  `rrf_k` × 两路权重 × 池深（`k` 与池深必须同变，否则单独扫 `k` 没有意义）；
  查询整形态（并集/交集/短语/前缀）；挖掘系数 × 加权形式（乘法/加法/排名偏移）。
- **跨夹具稳健性**：先求每个夹具的最优，再选出"最差夹具损失最小"的公共取值，
  同时报告该取值相对各夹具自身最优的差值（regret）。只按合并均值选参会被大夹具带偏。
- **噪声带**：同一默认配置连跑三次，把观察到的最大抖动记为噪声带；变体差值落在带内
  一律标记为平手，不据此改默认值。真实模型的提供方漂移也必须落进噪声带口径。
- **记录**：每次扫描落盘设置快照、提交标识、模型名与夹具指纹，报告由脚本直接生成，
  不再手工维护结论表。

## 四、真实 BM25 基线

### 基线定义

"全文单路"要成为基线，需要满足三条：分泳道可分解、与融合同池同深度、与自身变体成组。
据此引入三条单路矩阵行（全部复用现有生产原语，不新增生产代码）：

- 双泳道全文（现状默认）：全文索引覆盖两条泳道，与融合共用同一索引。
- 仅向量泳道全文：与向量索引同域对照，用来剥离"双泳道索引差异"这一混杂因素。
- 仅向量：无全文参与，读 `_rrf_scores` 在全文权重为零时的退化行为。
- 全文变体组：列权重、查询整形（并集/交集/短语/前缀）、池深、泳道范围各自成行，
  基线取该组在 dev 上的最优值，而不是固定为生产默认值。

对齐规则必须写进报告：池深一致（当前全文路取 25 条后按分组去重、融合路每路 30 条，
不等，需要显式声明或拉平）、去重与折叠一致、装配与截断一致、`k` 一致。

### 需要采集的量

- 每条查询的完整排名行（现有实现已保留），加上原始分：全文 BM25 原值、余弦值、精排分。
- 池级诊断：在池深 10/30/100 上的池召回（答案是否落在池内）、池内 oracle nDCG@5
  （池内最优排序能到多少）、两路前 k 集合的重合度、两路排序的秩相关。
  这两个量把"聚合丢分"与"召回丢分"分开：池召满是聚合问题，池召不满是召回问题。
- 延迟：分方法给每查询 p50/p95，含查询向量编码成本。

### 判读方式

- 池召回已满而 oracle 与实际的差很大 ⇒ 聚合方式值得换，继续做下一节的矩阵。
- 池召不满 ⇒ 先改召回预算、分块与查询整形，换聚合方式没有意义。
- 两路排序高度一致 ⇒ 聚合选择的收益上限低，应优先保简单方案（排名融合），
  把预算投到精排或召回上。
- 中文与非拉丁查询要在这一层单独看：若全文池召回接近零，则任何全文参与都是噪声权重。

### 代码落点

基线行与聚合候选都是纯函数，放在基准目录内，直接消费 `fts_search` 的 id 与分值、
向量存储的 id 与分值，以及生产装配函数；排序与指标复用现有指标模块。
生产侧在决策之前不动。决策定下来后，就地替换 `HybridRetriever` 的打分实现，
不新建并列融合模块，也不保留旧分支；基准侧的候选实现随之删减为"被采纳方案 + 基线"两行。

## 五、聚合方法对比

候选必须建立在同一索引、同一池、同一 `k` 上，且全部在真实模型下跑：

- 排名融合（现状）：`k` 与两路权重按池深联调。
- 归一化加权和：每查询最大归一化、最小最大归一化、z 分数；权重按凸组合扫。
- 全文分饱和 + 余弦的凸组合：全文原值重尾（4～33），需先映射到有界区间。
- 计数型融合（CombSUM / CombMNZ 类）：与被两路同时命中的次数相乘，
  与现有"按支持度乘法加权"的形态同族，便于对比。
- 精排与融合的关系：当前实现是头部用精排分替换、尾部保留融合分，形成尺度断点。
  需对比三种：精排替换、精排与融合分混合、精排仅重排头部的顺序而不改分值。

挖掘加权的形式要与聚合一起选，不能分开调：乘法叠加在归一化分上、加法叠加在归一化分上、
以及"作为排名偏移的一小步"。判定标准是同一权重下不同聚合方式的相对顺序是否稳定。

决策规则固定为：合并口径下优于基线且差值超过噪声带、最差夹具不退化、延迟不超上限；
三项同时满足才改默认值。满足后写入门禁：融合不得低于基线减去噪声带，
并保留基线行作为长期对照。

## 六、容易踩的坑

- **双泳道索引不对称**：全文索引包含为词法匹配专门切出的辅助块，向量索引不含；
  直接比较两路等于比较两个索引规模。基线必须给"仅向量泳道全文"这一行。
- **池深不齐**：全文路 25 条、融合路每路 30 条，会把召回差异算进方法差异。
- **替身替掉了问题**：离线替身与 BM25 同源，融合几乎必胜；聚合结论不得由替身产生，
  报告要显式标注哪些行是"仅示意"。
- **判定集共享**：调参与门禁用同一批查询会把噪声固化成下限，必须 dev/test 分开。
- **同库双夹具**：文档与源码同属一个库，两夹具强相关，合并统计会重复计权；
  合并口径只用于选参稳健性，不用于显著性判断。
- **提供方漂移**：真实模式同查询两次调用差约 1e-3，足以换位近似并列的结果；
  跨轮比较只比同轮相对差异。
- **探针归属**：多夹具后探针要按夹具类型分配（文档类跑材料预算与置信度，
  源码类跑副表成本），不能默认挂在 `docs` 上。

## 七、项目粒度：下载与评分怎么拆

外部实现 `code-context-engine` 的基准组织方式可作对照。两者获取方式不同，结论不能照搬，
但它的取舍已经把成本记在了文档与工具里，值得逐条吸收。

### 外部实现的做法

- 夹具是**入库的真实工程源码**，按语言分目录、放在独立仓库（子模块）里，不下载；
  九个项目（Python 的 flask、Rust 的 once_cell 与 ripgrep、Go 的 gin、JavaScript 的 express、
  Java 的 spring_boot 与 jackson_core、C# 的 mediatr、C++ 的 media_server）各配一套判定集，
  每个项目再绑一个同语言的干扰夹具构成负样本池。
- 判定集**按项目一模块**，每个项目约 40～45 条查询，落点是源码行区间，带强相关/一般相关
  两级，查询类型分限定符号式、词面扰动式、语义式。
- 共享的只有评分与报告代码：区间重叠评分器、分组聚合、报告写出各一份；项目只贡献数据。
- 集中注册表把"项目 → 目标夹具、干扰夹具、判定集、语言、枢纽实体"绑在一处，
  新增项目只加一个清单条目。
- 入库的代价被如实记录：源码变动后行号漂移，判定集要重锚（ripgrep 明确写出某几个文件
  行号整体 -2 / -1，两条查询改判到新位置、与改造前的指标不可比），并专门写了一个
  行区间体检工具检查越界与空行边界。
- 规模档位规划了但长期留空，文档里写着"补齐前不要引用"；性能脚本的可选夹具也只有两个，
  与九套判定集并不对齐。

### 不按项目拆下载脚本，按项目拆获取配方

我们的获取只有两种形态（抓文档站、克隆仓库），对每个项目都是同一段代码，差异只在入口地址、
页数上限、抓取延迟、仓库地址、子目录、固定标签这些参数。拆成每项目一个脚本，等于把已参数化
的流程复制 N 份，改一处要改 N 处，而且没有任何一处表达出"这个项目的获取方式确实不同"。

真正需要按项目独立的是配方：入口、上限、延迟、仓库、子目录、固定标签、期望规模、语言期望。
这些放进同一份规格文件的条目，一个下载器跑全部。判据只有一条：某项目的获取在结构上不同
（需要多仓合并、子模块展开、抓取后再生成），才在同一模块里加一条专属获取步骤；
"项目更大"或"项目更多"不是拆脚本的理由。

### 评分体系按项目拆数据，不按项目拆代码

- 每个项目一份独立判定集文件，便于单独评审、单独废弃、单独 diff，不做成一个大文件加键。
- 指标、排名行、聚合口径只有一份实现，避免不同项目的召回定义分叉而失去可比性。
- 门禁按项目分条，下限只能从实测得出，不给全局默认值再回退。

判定集比现状要多带的字段：归属分支（文档、源码、跨分支）；查询类型，且类型必须与评分代码里的
枚举同源（外部实现曾出现游离在枚举与过滤之外的裸字符串类型）；相关等级（强相关、一般相关），
用来区分命中了目标实体与命中了同文件邻接实体；数据划分（调参、门禁）；干扰语料指定。
跨分支查询（某段文档描述某个源码文件）是文档与源码同库才有的类型，外部实现没有这一档。

### 先下载再定题目，但锚点用身份不用行号

外部实现的顺序正是先有夹具再写行区间，因为行区间只能对着磁盘源码写。我们的现状锚点是绝对地址
与仓库相对路径，抗更新强，但只能判到文件级，判不出"同一文件里命中了错的那个函数"，
而这恰是分块检索要回答的问题。

因此锚点记录身份而不是位置：标题路径、分块标识、限定符号名、段落分组标识；评测时用身份到当前
语料里解析成实际分块与行号。这样先下载后定题的工作流成立，重新下载或切换标签都不会让判定集
失效，也免掉外部实现那样的重锚成本。

三阶段，每阶段有产物与检查点：

1. 获取与体检：跑配方，产出语料报告（页数、分泳道块数、文件数、实体与调用数、挖掘规模、
   语言分布、耗时）。体检不过即失败——页数为零、语言检测为零、解析率不达标都算失败，
   不落成空目录，也不进下一阶段。
2. 侦察与起草：在已建库的数据集上浏览与检索，起草查询，锚点从库里解析并自动校验
   （可解析、唯一、非空结果、不属于无答案类型）。产物是标记为草稿的判定集，允许不完整。
3. 冻结：拆成调参与门禁两份，按实测值减噪声带设下限，登记进项目清单与门禁文件。
   未冻结的项目不进门禁，也不进方法矩阵。

### 评估变体按项目声明

外部实现有"全量/去测试/仅实现"与"精确区间/整组填充"两组评估变体，原因是仓库里测试与示例
代码占比差别很大，不声明就会把示例代码算进召回。我们的语料是库不是应用，现有夹具靠子目录
规避了这一点，但换整仓索引就会暴露。每项目在配方里声明：索引范围（子目录或全仓）、
评测范围（全量或仅实现）、文档分支是否参与。

### 规模控制与反模式

不做每项目全矩阵，分三档：参考档两到三个项目跑方法矩阵、聚合对比、参数扫描与统计口径；
回归档其余项目只跑默认行，只吃不变量与项目下限；干扰档是与语言无关的小型无关语料，
只用于构成负样本池，不单独设门禁。

要避开的外部实现反模式：空占位夹具（规划了档位长期留空，文档还得写"补齐前不要引用"）；
每项目一套评分代码；手工维护的矩阵文档（几十条组合与数周计划未落地即成为负担，矩阵必须由
脚本产出，文档只放结论与复现命令）；判定集与夹具同生命周期（身份锚点可解耦）。

## 八、数据固定与路径解耦

获取应当只做一次，之后只用固定数据；但"一次性"必须落实为"不可变且可校验"，否则只是约定。

### 改造前的四个漏点

- 生产快照库与克隆直接写在夹具目录下，且用的是生产命名层级（快照按生态/库/版本，克隆同样），
  比基准需要的多两级；生态还被写死成 `custom`，与规格里的 `pypi` 不一致。
- 快照库是带配额的生产存储（抓取时传 256MB），会按配额淘汰正文；而导出器只读快照库，
  正文缺失就少导出页面且不报错。也就是说，一次重新抓取可能**静默换掉语料**。
- 清单里记的是绝对路径（页面缓存、克隆目录），换机器或换检出位置即失效，而构建直接依赖它们。
- 漂移目前仅靠"不传刷新参数就复用"这一习惯；谁跑了刷新，全部门禁下限就悄悄失效，
  且新旧语料的报告无法比较。

### 两个平面

获取平面是临时的、可丢的、构建永不读：生产快照库与克隆都落在临时目录，抓完导出后整体删除。
这一层保留生产命名与配额逻辑，因为它验证的正是生产获取链。

夹具平面是不可变归档，是构建的唯一输入，按"项目/分支"两级，一目录一份：

- 文档分支：一个原始正文的压缩行文件。现状已经是原始正文而非净化文本，这点必须保留——
  只有输入相同，净化与分块的改动才能在相同基础上比较。
- 源码分支：固定提交的工作树打包，不含版本库目录。理由有三：它是活对象库（可被拉取改动）、
  体积数倍、且是多余层级；文件遍历本来就跳过它，去掉不影响解析。代价是仓库管理器对无版本库的
  本地目录会把提交标为本地，因此提交标识必须由归档元数据携带，并由数据集清单记录，
  不依赖检出目录自省。
- 元数据：配方摘要（入口、上限、延迟、仓库、子目录）、获取时间、提交或页集合摘要、
  载荷摘要与修订。

### 冻结与校验（已落地）

- 获取先导出到暂存目录，成功后才落到归档，因此抓取失败不会破坏已有语料；
  已存在的归档只在显式要求重新获取时替换。
- 归档写完后重读一遍比对内容摘要，再置为只读，把约定变成机制。
- 构建与评测只读夹具平面：先校验身份、获取配方与载荷摘要，消费时再重算页集合摘要或
  源码树摘要，任何不一致都是硬失败。配方也比对，所以改了规格却没有重新获取会被挡住。
- 修订是载荷摘要的前 12 位，不另设标签旋钮，因此不可能与实际内容脱节；数据集清单与报告
  都记录修订。
- 门禁下限绑定到修订：档案记录的修订与数据集修订不一致即失败，提示重新测量下限。

### 路径解耦的具体形态

- 夹具路径不再携带生态、库、版本等身份信息（身份放元数据），目录只表达"哪个项目、哪条分支"，
  这样路径稳定、层级最少，且与判定集的分支键天然一致。
- 清单不出现绝对路径，构建从夹具根解析。
- 构建不再向数据集目录下建克隆目录；数据集是派生文件、重建即可，库内留绝对路径可接受，
  但不得成为任何判定的输入。
- 临时快照库消掉了配额这个旋钮：容量淘汰不再可能截断导出，获取也不再为夹具单设容量。
- 数据集目录只保留数据库与清单：归档源码解包在临时目录里完成索引后即删除，既不生成空的
  克隆目录，也不把第三方源码落到仓库内（否则会被工具链收进测试发现）。

### 代价与护栏

获取链改为只用一次，就不能只靠基准验证它：生产抓取、克隆与解析的回归仍留在端到端用例，
基准不承担获取回归职责，反过来获取用例也不读基准归档。

归档仍不入库；跨机器离线拷贝一份归档即可，不为它新增配置开关。
新增项目是"加一份归档加一份判定集"，不触发修订；重新抓取是"新修订加重测下限"。
这两件事在流程上分开，是避免漂移的唯一可靠分界。

## 九、归档的消费：解包与读取

### 两条分支的读取方式不同

- 文档分支不解包。载荷是一个压缩行文件，读进内存后逐行 JSON 解析，交给生产的净化与分块：
  这两步是纯文本函数，只吃正文、内容类型与 URL，不碰文件系统。当前 23 页、正文合计 0.97MB，
  读取约 9ms。
- 源码分支必须解包。生产的索引路径是"目录 + 相对路径"：文件遍历用递归匹配、按后缀过滤、
  跳过测试目录与超大文件，随后逐文件按相对路径读字节；解析缓存写在数据库表里（键为仓库、
  路径、指纹、配置版本），源码目录旁边不落任何文件。只有落成真实目录才走得到这条路径。
- 解包落点：每次构建解到临时目录，先校验源码树摘要再索引，构建结束即删除。实测解包
  35～47ms、摘要 7～12ms，而源码分支构建整体约 0.8s，解包占比不足一成。

### 是否在本地展开

要展开，但只在构建期间展开，理由三条：

1. **保真**：不展开就得给基准另写一条"从压缩流里读文件"的旁路。那是生产永远不会走的代码
   路径，测出来的结论与线上无关，也正是本项目禁止的平行实现。
2. **工具卫生**：把第三方源码长期落在仓库树里，`pytest` 会去收集它（此前把树解到数据集目录时，
   直接撞上第三方测试目录的配置文件并触发导入路径冲突），`ruff check tests` 会去检查它
   （此前正是因为这一路径需要专门的文件级豁免）。解到临时目录、用完即弃，两类问题都不存在，
   也不需要维护豁免清单。
3. **没有收益**：持久缓存解包结果只省几十毫秒，却引入跨轮状态与失效判断。构建本来就每次
   重建数据集，下游产物全由归档与代码版本决定，缓存只会多一个漂移面。

### 明确排除的两种形态

- **载荷存成目录树**：省掉解包，但第三方源码就长在仓库树里，工具卫生问题回来；冻结口径也从
  "一个文件一个摘要"退化成逐文件校验，复制与核对更容易只拷一半。
- **按修订命名的持久解包缓存**：省 40ms 左右，换来陈旧状态与失效判断，本轮实测数据不支持。

### 生产为什么不采用归档

归档优化的是整体不可变、单一摘要、整体复制、一次性消费；生产恰好需要相反的三件事：
按文件随机访问（热更新与按文件复用解析缓存）、按版本目录回收（配额与保留策略）、
原地增量（版本库本身已内容寻址且可拉取）。打包会同时让这三件事退化，所以生产保持
"版本库目录 + 按 URL 键的快照 blob"，路径里的生态、库、版本三段就是身份本身。
基准能把身份挪进元数据、把路径压成两级，前提是它每个项目分支只要一份、永不原地更新、
没有配额回收。

### 与生产代码的关系：统一什么，不统一什么

生产与基准走的是同一套索引与检索函数，差异只在输入物化。判断标准是"会不会让基准测到生产
不走的代码路径"，不是"代码能不能合并"。

已经共用（基准只是编排，不复制实现）：`index_repo` 的显式本地源分支（生产命令行本来就支持
按本地路径索引，基准走的就是这个入口）、文档净化和双泳道分块、页面落库、解析与挖掘、
检索服务与混合检索、全文读取、嵌入文本拼装、材料预算与引用过滤。

本轮顺手消掉的重复：向量泳道判定（"仅全文块不进向量索引"）原先在生产维护模块里写了三处
SQL 片段，基准又照抄了第四份。现在收敛到嵌入文本模块一处：Python 判定
`is_embeddable_metadata` 与 SQL 片段 `EMBEDDABLE_SQL_CONDITION` 并排放置并注明必须同步修改，
生产维护模块的三个查询与基准的取行查询都引用它。

保持不同（差异来自输入物化，不是逻辑分叉）：

| 维度 | 生产 | 基准 | 为什么不合并 |
|---|---|---|---|
| 获取 | 联网抓取与克隆，带复验与配额 | 归档只读 | 生产要增量复验；基准要冻结语料 |
| 源码物化 | 持久可写克隆，原地更新 | 临时解包，用完即删 | 生产要热更新与回收；基准要零漂移 |
| 向量存储 | simvec/qdrant，带水位与漂移重建 | 进程内余弦，同一嵌入文本约定 | 基准判的是排序质量；联网库会毁掉离线门禁 |
| 来源标识 | 版本库提交号贯穿调用记录 | 本地标记加归档元数据 | 归档里没有版本库，提交号由元数据携带 |

由此留下的覆盖缺口，明确记录而不在基准里补：基准看不到向量存储的版本过滤与漂移降级，
也看不到"同一版本换源"的保护，以及增量更新的复用路径。这些由向量存储、代码索引与
运维路径的集成用例覆盖，职责不重叠。

### 已知取舍

- 构建结束后，数据集里的仓库记录指向已删除的临时目录，提交字段是"本地"。两者都不参与任何
  判定（基准始终显式传入源码路径），权威的提交与来源记在归档元数据与数据集清单里。
- 文档载荷逐页流式读取，内存只与单页正文有关；内容摘要核对也走同一迭代，不保留整语料。
- 构建只接受空目录或只含数据集已知成员的目录，传错路径会被拒绝而不是先删再建。

## 十、落地顺序

已完成：归档化（临时获取层、按项目分支的两级归档、元数据与摘要校验、只读冻结、修订绑定门禁）、
