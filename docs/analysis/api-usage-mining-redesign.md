# API 使用特征挖掘改造设计

本文分析当前 API 特征挖掘的来源偏差，并给出面向“库使用问题”的目标设计。核心结论是：**库源码适合作为 API 定义来源，不应默认作为 API 使用模式来源**。使用模式应以官方示例、文档代码块、演示应用和受控参考项目为主，并且每条调用实例都必须带来源角色、样本身份和版本约束。

本设计不保留旧口径的隐式兼容。若确实需要分析库内部实现，只能作为显式、独立、带说明的挖掘档案，不能继续作为用法推荐的默认语料。

## 一、当前设计的问题

### 1. 定义来源和使用来源被合并

当前源码链为“目标库版本 → 一个仓库地址 → 一批源文件 → 声明与调用 → 挖掘”。相关入口和中间环节包括：

- `services/code/repo_source.py::lookup_index_source_cached` 为目标库版本解析单一仓库地址；
- `services/code/code_ingest.py::_index_repo_inner` 克隆该仓库，枚举受支持后缀的文件，并拒绝同一版本使用另一个来源；
- `services/code/repo_collect.py::_collect_decl_index` 从同一批文件抽取 `api_entities`；
- `astminer/resolution.py::resolve_calls` 用同一批文件的声明和别名解析这批文件中的调用；
- `services/code/mining_refresh.py::mine_patterns` 把全部调用按 `caller_file::caller` 分组后做闭合序列挖掘。

这意味着库自己的实现文件、内部辅助函数、构建脚本和测试夹具与官方示例一起进入频次、共现、特征树和 PrefixSpan。对“库应该怎么用”这一问题，这些信息大多是噪声：它们表达的是库内部如何实现，而不是调用方如何组合 API。

### 2. 数据模型没有语料角色

`call_instances` 记录了 `repo`、`caller_file`、`resolve_kind`、置信度、行范围等，但没有表达：

- 这是官方示例、文档片段、参考项目、测试还是库内部实现；
- 这属于哪个示例文件、哪个文档代码块、哪个参考项目函数；
- 目标是当前库版本中的哪个 API，是否命中目标 API 集合；
- 该来源应以何种权重、何种样本上限参与挖掘。

`repos.name` 当前基本是“生态/库/版本”，也不适合表达同一目标版本下多来源并存。`call_uid` 虽然包含仓库名，但仅解决身份唯一性，不能替代语义上的来源分类。

### 3. 现有过滤解决的是另一类问题

`resolve_kinds` 和审核状态能排除待定、冲突、标准库与内建调用，但它们解决的是“解析是否可信”，不是“语料是否适合作为用法样本”。一个完全解析成功的库内部调用仍然会污染用法分布。

`include_ambiguous` 同理，只调整解析置信口径，不调整语料角色。

### 4. probe 与索引可手动选文件，但不能形成可复用语料

`probe-repo` 能给出目录树、采样、子目录限定、单文件限定和排除规则，索引侧也接受相同参数。这足以临时把范围收敛到 `examples/`，但存在三个问题：

- 选择不持久化，无法把“DPDK 官方 examples + MTL 中 DPDK 相关调用”保存为稳定语料集；
- 选择不带角色和权重，无法参与可复现的挖掘配置；
- 再次索引时按当前文件集合清扫旧调用，不能累计多个来源。

### 5. 文档代码块只进入检索，没有进入挖掘

`crawler/extract.py` 会保留 `pre/code`，`chunking/splitter.py` 会保持围栏平衡，因此文档里的代码块目前能作为文本被检索和问答引用。但这些代码块没有被解析成调用实例，也没有与标题路径、URL、围栏序号绑定成样本。

### 6. 顶层示例会被现有挖掘直接丢弃

`mine_patterns` 要求调用有非空 `caller`。Python 脚本式 example、Markdown 代码块、C 示例中的顶层初始化、Rust 文档片段等经常没有函数级 caller。即使把这些文件加入现有索引，它们也不会形成序列。

### 7. 支持度语义不适配异构小样本

当前支持度接近“调用条数/作用域数”。官方 example 与文档片段通常数量少但质量高；参考项目数量大且场景偏置明显。若直接按调用条数计支持度，大仓库会压倒官方示例；若沿用默认 `minsup=2`，少量高质量示例又可能无法形成模式。

### 8. C/C++ 场景当前不可用

`astminer/config.py` 和 `pyproject.toml` 没有 C/C++ grammar 与语言配置。以 DPDK 为目标库、MTL 为参考项目时，现有解析链无法解析这类源码，也无法处理 DPDK 中大量函数式宏调用。

## 二、目标架构

### 1. 拆成两条职责独立的链路

```text
目标库 API 定义来源
  库源码 / 头文件 / rustdoc 等
      → api_entities、签名、参数、返回类型、层级、目标 API 集合

用法语料来源
  官方 examples / 文档代码块 / README / 演示应用 / 参考项目 / 手工片段
      → usage sample → 调用实例 → 频次、共现、特征树、序列模式
```

目标库源码仍然需要索引，但它的默认职责是提供 API 事实。库内部实现调用不进入默认 usage profile。只有显式选择 implementation 档案时，才分析内部实现调用。

用法语料解析时可以使用源仓库自身的局部声明和别名来解析调用，但不得把这些局部声明写成目标库的 `api_entities`。是否属于目标 API，由解析结果与目标 API 集合或目标命名空间规则决定。

### 2. 关键数据对象

#### 代码语料源

新增语料源实体，至少包含以下信息：

| 字段组 | 内容 |
|---|---|
| 绑定关系 | 目标库版本、租户 |
| 身份 | 来源键、URL 或本地路径、仓库 commit、站点地址、手工片段标识 |
| 角色 | `official_example`、`doc_snippet`、`readme`、`test`、`reference_project`、`implementation` |
| 形态 | `repo_file`、`html_code_block`、`markdown_fence`、`rustdoc_doctest`、`manual_snippet` |
| 选择规则 | 子目录、包含与排除规则、单文件限定、语言、标题路径、代码块序号 |
| 目标约束 | 目标 API 前缀、限定名集合、允许与拒绝规则、目标库版本兼容策略 |
| 采样约束 | 权重、每文件上限、每来源上限、每项目上限 |
| 运维 | 是否启用、来源指纹、创建与更新时间 |

角色必填。未知角色应直接报错，不能静默归为内部实现或官方示例。

#### 调用实例

`call_instances` 在现有字段上补充：

- 语料源引用；
- `sample_id`：一个示例文件、一个文档代码块、一次 doctest、一个参考项目函数或一个手工片段；
- 来源形态和角色快照；
- 是否命中目标 API；
- 目标库版本兼容状态；
- 证据定位信息：文件与行范围，或 URL、标题路径与围栏序号。

调用身份应纳入语料源和样本身份，避免不同来源的相同相对路径和字节区间碰撞。

`in_target_api` 是布尔事实，不替代审核状态。审核仍负责处理歧义、冲突和批准语义。

#### 挖掘档案

新增挖掘档案实体，描述一次派生结果的完整输入口径：

- 目标库版本；
- 参与的语料源集合；
- 角色权重和支持度口径；
- 目标 API 过滤；
- 去重策略；
- 序列长度、最小支持度等参数；
- 解析配置指纹、语法指纹、来源选择指纹。

`seq_patterns`、`feature_nodes`、`api_clusters`、`pattern_labels` 按挖掘档案隔离，而不是只按库版本隔离。否则同一版本下切换语料来源后，旧支持度和新支持度会相互覆盖，问答中的模式标签也无法解释来自哪套语料。

## 三、样本与序列语义

### 1. 样本边界

样本边界由来源形态决定：

| 来源 | 默认样本 |
|---|---|
| 示例源码文件 | 文件；若文件含多个函数，可按函数切分 |
| 参考项目源码 | 调用函数；顶层或全局初始化按文件处理 |
| 文档代码块 | 单个围栏代码块 |
| Rust doctest | 单条文档测试代码 |
| README 片段 | 单个围栏或缩进代码块 |
| 手工片段 | 单条提交片段 |

每条样本保留稳定的 `sample_id`。同一文档块被 Markdown 和 HTML 同时发现时，应先归一到同一文档身份，再按围栏序号生成样本。

### 2. 序列分组

序列以 `sample_id` 为主键分组，组内按字节顺序或代码块顺序排列。`caller` 作为组内结构信息和证据字段保留，但不再作为唯一分组键。

这样可解决两类现有问题：

- 顶层示例没有 caller 也能参与挖掘；
- 一个文档代码块中的多行调用不会因为缺少函数上下文被丢弃。

### 3. 支持度

默认支持度改为“包含该模式的样本数”，而不是原始调用条数。另保留以下可审计指标：

- 调用出现次数；
- 不同文件数；
- 不同语料源数；
- 不同项目数；
- 按角色加权的支持度。

加权只影响排序，不覆盖原始支持度。参考项目贡献应设上限，避免单个大项目主导分布。官方 example 可使用较低最小支持度，但必须通过目标 API 命中、解析质量和去重门槛；参考项目建议从样本支持度二起。

### 4. 去重

同一示例常同时出现在 README、文档站和仓库 `examples/`。去重键建议使用语言、目标 API 调用序列、参数形状的规范化结果。重复样本不重复计数，但保留各自证据链接；展示时优先官方来源。

### 5. 过滤顺序

挖掘输入按固定顺序处理：

1. 审核状态过滤：冲突排除，待定默认排除；
2. 目标 API 过滤：默认只保留命中目标 API 集合的调用；
3. 标准库与内建过滤：沿用现有 `resolve_kind` 规则；
4. 来源质量过滤：解析失败、占位符、伪代码、截断片段排除；
5. 样本上限与去重；
6. 序列组装与 PrefixSpan。

非目标 API 调用可以保留在调用实例表中供上下文查看，但默认不进入模式输入。

## 四、语料发现与适配器

### 1. 仓库内示例的常见模式

目录名只能作为候选信号，不应作为唯一依据。建议先由 probe 给出候选，再由使用者确认并固化为语料源。

| 类型 | 常见形态 |
|---|---|
| 通用示例 | `examples/`、`example/`、`samples/`、`demo/`、`demos/`、`playground/`、`sandbox/`、`quickstart/`、`tutorial(s)/`、`cookbook/` |
| 文档旁示例 | `docs/examples/`、`docs/tutorials/`、`website/examples/`、`site/content/docs/*/example*` |
| Rust | `examples/*.rs`、`tests/*.rs`、`src/bin/`、演示 crate、模块文档里的围栏代码 |
| Go | `example_test.go`、`func ExampleXxx()`、包注释示例、`cmd/` 下的命令入口 |
| Java/JVM | Maven 或 Gradle 的 `*-example`、`*-demo`、`*-samples` 模块；`src/test/java` 下的 Example/Demo；Spring 的 `*Application` |
| Python | `examples/`、`docs/source/examples/`、`notebooks/`、README doctest、顶层脚本 |
| JavaScript/TypeScript | `examples/`、`apps/demo`、`packages/*/examples`、`*.stories.tsx`、sandbox |
| C/C++ | `examples/`、`apps/`、`demo/`、`test/`；DPDK 的 `examples/` 是典型形态 |

候选置信度可综合路径命中、文件名、构建入口、README 引用和调用密度，但最终选择应显式固化。

### 2. 文档代码块适配器

文档链在正文清洗与分块之间增加代码块抽取：

- HTML 文档优先从清洗后的 `code`/`pre` 节点读取语言类和文本；
- Markdown、MDX、RST、AsciiDoc 从围栏或 literal block 读取；
- 每个代码块记录 URL、标题路径、围栏序号、语言标签；
- 代码块以合成文件名送入现有 AST 引擎，语言由标签决定；
- 解析结果绑定原始页面和标题路径，作为证据；
- 质量门槛排除输出块、shell 会话、diff、占位符、截断片段和无法解析的混合语言块。

现有 `documents.metadata` 中的标题和路径可用于证据展示；新增代码块不需要改变文档分块和全文索引逻辑。

### 3. Rust 适配器

Rust 适合形成高质量用法语料，来源优先级如下：

1. `examples/*.rs`：正式示例，优先级最高；
2. `tests/*.rs`、`src/bin/` 和演示 crate：次高；
3. 模块文档和 crate 文档中的 fenced code block；
4. README 与文档站中的 Rust 代码块；
5. 若工具链提供 rustdoc JSON，可作为文档注释和条目关系的补充来源。

当前 Rust 查询已有 `doc_comment` capture，可在此基础上解析围栏。Rust 标记按用途处理：

- `no_run`：参与挖掘，表示可编译但不执行；
- `should_panic`：参与挖掘，属于可执行示例；
- `compile_fail`：只作反例材料，不进入正向模式；
- `ignore`：默认不进入正向模式，可单独保存。

每个 doctest 是独立样本，证据指向源文件行或 rustdoc 条目加围栏序号。

### 4. 参考项目适配器

参考项目是“消费目标库的项目”，不是目标库自身的另一个版本。注册时必须绑定：

- 目标库与版本；
- 参考项目 URL 与 commit；
- 目标 API 过滤规则；
- 每项目、每模块、每文件的贡献上限；
- 参考项目使用的目标库版本约束。

参考项目来源可以由人工声明，也可以从依赖清单、仓库搜索或索引申请中候选生成，但必须 pin commit 并显式批准。不得自动无限抓取下游仓库。

## 五、probe 的改造

### 1. 保持只读，选择另行写入

`probe-repo` 和 `probe-docs` 继续保持只读。probe 只回答“有哪些可用候选”，不注册语料源。使用者确认候选后，通过明确的注册动作写入语料源。

### 2. 仓库 probe

在现有目录树、采样、后缀统计、子目录、单文件和排除规则基础上，增加：

- 示例候选目录及命中规则；
- 候选文件路径、语言、推测入口；
- README 或文档对候选路径的引用；
- 每个候选中目标 API 调用的粗粒度数量；
- 文件是否可能是测试夹具或生成代码。

输出应让调用方能够直接选择一组文件并保存为语料源，而不是只给出裸目录列表。

### 3. 文档 probe

在现有前缀分组和采样基础上，增加：

- 每页代码块数量；
- 代码块语言分布；
- 标题路径中含 `Examples`、`Tutorial`、`Quickstart`、`Usage`、`Cookbook` 的页面标记；
- 每个代码块是否可能可解析；
- 代码块数量是否超预算。

通过 probe 选定页面和代码块规则后，注册为 `doc_snippet` 语料源。

### 4. 远程与本地边界

CLI 可继续接受本地路径用于 probe 和调试。MCP 与 Web 入口继续拒绝本地路径，避免远程调用方枚举服务端文件系统。远程语料源注册必须提供可解析的 URL 和 commit。

## 六、挖掘、阅读与检索消费

### 1. 挖掘入口

`mine` 从“库版本 + 参数”改为“库版本 + 挖掘档案 + 参数覆盖”。档案决定默认语料集合和权重，显式参数只做局部覆盖，不产生隐式默认。

若未注册任何 usage 语料，挖掘应明确返回空结果并提示缺少 usage source，而不是退回到库实现调用。

### 2. 读模型

`api-insight`、`pattern-insight` 和 `call-insight` 增加按来源角色、语料源、样本形态和挖掘档案过滤。每条证据展示来源标记：

- 官方 example；
- 文档代码块；
- 参考项目；
- 测试；
- 内部实现。

来源标记只用于解释和筛选，不替代审核状态。

### 3. 检索与问答

检索重排使用的频次和共现来自显式挖掘档案。问答中的模式标签必须绑定档案指纹，避免切换语料后仍展示旧标签。

面向用法回答时，默认档案只包含 usage 来源。参考项目特有的模式应在展示中保留来源提示，避免被解释为官方推荐。内部实现档案不参与默认问答材料。

## 七、DPDK 与 MTL 场景

### 1. 目标

目标库是 DPDK 某版本，参考项目是 Intel MTL。期望得到“在媒体传输和高速包处理场景下，DPDK API 的使用特征分布”，而不是“MTL 整体代码的调用分布”。

### 2. 前置能力

需要新增 C 语言支持：

- C grammar wheel；
- `LanguageConfig`；
- C 的声明、调用、宏调用和包含关系查询；
- 调用实例中对函数式宏的识别。

tree-sitter 能抽取直接 `rte_*()` 调用和显式宏调用，但无法完整还原宏展开后的间接调用。系统应记录宏覆盖率，并在证据或健康统计中标明该限制；后续可结合 DPDK 头文件中的宏定义做补充分析。

### 3. 处理流程

```text
DPDK 目标版本
  → 解析头文件与源码
  → 建立 rte_* 函数、宏、类型和签名集合
  → 形成目标 API 事实

MTL 参考项目
  → pin commit
  → probe 选择消费 DPDK 的源文件
  → 以 DPDK 事实解析调用
  → 只保留命中 rte_* 或目标 entity 集合的调用
  → 按函数或文件切分样本
  → 标记 MTL 使用版本与目标版本是否一致
  → 生成 dpdk-on-mtl 档案
```

### 4. 版本一致性

MTL 可能绑定旧版 DPDK。若调用无法解析到目标版本 entity，应标记为版本不一致并排除出当前版本主分布。可另存迁移或兼容材料，但不能混入当前版本的用法特征。

### 5. 档案比较

至少保留两个独立档案用于比较：

- `dpdk-official-examples`：来自 DPDK 官方 `examples/` 与文档示例；
- `dpdk-on-mtl`：来自 MTL 参考项目。

两者可并列展示频率、共现和序列模式差异。比较结果表达场景差异，不自动合并为单一全局排行。

## 八、编排与边界

- `services/code` 负责注册语料源、执行定义抽取、执行 usage 摄取、触发档案重算；
- `astminer` 和 `mining` 保持纯内存算法，不直接依赖数据库；
- `db` 负责 schema、迁移和事务；
- `crawler` 负责文档与仓库获取，不决定挖掘角色；
- CLI、MCP、Web 只做参数透传和结果格式化。

新增语料源、档案和索引任务应纳入版本锁和断点续跑。语料源注册是幂等操作，以来源身份、commit、选择规则和目标版本构成身份。

## 九、质量门槛

进入 usage 挖掘前逐条检查：

- 代码块或文件解析成功；
- 语言标签或后缀可识别；
- 至少命中一个目标 API；
- 不含明显占位符、截断标记和纯输出文本；
- 调用解析不是冲突状态；
- 目标库版本兼容；
- 重复样本已归一；
- 来源角色和权重明确。

参考项目还需满足项目级上限和版本约束。官方示例可使用更宽松的解析门槛，但仍需通过目标 API 命中。

## 十、测试设计

需要补充或改造以下测试：

- 库内部调用不进入默认 usage profile，显式 implementation 档案可进入；
- 官方 example、文档代码块和手工片段各自生成正确 `sample_id` 和证据；
- 顶层 Python 示例无 caller 仍能形成序列；
- Rust `examples` 与 doctest 分类正确，`compile_fail` 不进入正向模式；
- 参考项目只保留目标 API 调用，版本不一致调用被排除；
- 样本支持度按样本数统计，大项目贡献受限；
- 重复示例只计一次支持度但保留多条证据；
- 挖掘档案指纹变化后，派生表独立重建；
- 审核冲突、待定、标准库和内建规则在 source-aware 链路上仍然有效；
- probe 输出与注册后的实际索引文件集合一致；
- Web、MCP、CLI 对语料源和档案参数的透传一致。

涉及挖掘逻辑变化的测试必须包含 golden 或 differential 用例，覆盖“内部实现污染前后”模式集合的差异。

## 十一、实施顺序

1. 补齐 schema 与迁移：语料源、调用实例来源与样本、挖掘档案、派生表档案维度。
2. 拆分定义抽取与 usage 摄取编排，让 usage 解析使用目标 API 事实。
3. 实现仓库文件适配器，优先覆盖官方 examples 与演示应用。
4. 实现文档代码块适配器，复用文档 URL、标题路径和围栏序号。
5. 改造序列分组、支持度、目标 API 过滤和去重。
6. 扩展 probe，使候选选择可以固化为语料源。
7. 增加 Rust examples 与 doctest 适配器。
8. 增加 C/C++ 语言支持，实现 DPDK/MTL 参考项目档案。
9. 同步更新 CLI、MCP、Web、配置、文档和契约测试；删除旧默认口径，不保留兼容回退。

## 十二、边界与限制

- 目录和标题模式只是启发式，不能替代人工确认；
- 文档代码块经常不完整，必须依赖解析与占位符门槛；
- 参考项目带场景偏置，只能作为场景档案，不能自动代表整个库生态；
- C 宏展开无法由当前 AST 解析完整覆盖，需显式记录覆盖率；
- 语料源权重必须可解释，不能用隐藏权重改变排序；
- 内部实现分析是另一种合法任务，但与用法挖掘必须隔离。

改造后的核心不变量只有一条：**每个进入挖掘的调用都必须能回答“它是谁的使用样本、属于哪个目标库版本、是否命中目标 API、证据在哪里”**。如果任一问题无法回答，该调用不应进入默认用法挖掘。

## 十三、当前落地范围

本设计已落到现有代码中：数据库新增语料源与挖掘档案；调用实例携带来源、样本和目标 API 命中状态；索引与文档抓取分别注册实现、示例、文档代码块和 Rust doctest 语料；挖掘与读模型按档案隔离；默认 `usage` 档案排除内部实现。C/C++ 的最小语言配置与查询已加入，用于参考项目中的直接目标 API 调用；宏展开和编译分支解析仍属于语言覆盖矩阵登记的后续缺口。
