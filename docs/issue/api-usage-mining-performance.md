# 用法挖掘链路性能问题与非必要分支

本文记录真实仓库用法挖掘链路的性能现象、已定位原因、可优化点，以及性能验证的补充方案。结论基于当前开发机实测，绝对耗时只用于说明量级，回归判定应使用相对基线。

## 实测现象

| 场景 | 规模 | 现象 |
|---|---|---|
| 原受控切片回放 | 实现 2、官方 3、参考 3 个文件 | e2e 约 5 秒，但结论不具代表性 |
| DPDK `lib/` 单独索引 | 895 个文件、19692 个实体、46231 个调用 | 约 62 秒 |
| DPDK `drivers/` 单独索引 | 2857 个文件，含生成型巨头文件 | 超过 10 分钟仍未完成，主动终止 |
| 完整角色语料回放 | DPDK `lib/` 895、DPDK `examples/` 233、MTL 262 | 约 3.5 分钟 |
| 完整语料使用 `minsup=1, minlen=1` | 目标调用数万级 | 超过 40 分钟仍未完成，主动终止 |
| 完整语料使用有界挖掘参数 | 支持度 3、长度 2–8、报告上限 50 | 回放约 3.5 分钟，输出稳定 |

## 已确认的性能问题

### 支持度为 1 的模式爆炸

序列模式在支持度为 1、最小长度为 1 时等价于枚举大量子序列。即使限定 API 名称集合，仍会产生数千条组合模式。此前“前 50 个 API 名称”的约束只限制名称，不限制模式数量，因此报告文件一度膨胀到两千多条，挖掘时间不可接受。

当前 e2e 已改为有界参数并限制报告条数。后续应把该边界提升为生产配置，避免其他调用方再次使用无界参数。

### 语料角色与全仓索引混淆

DPDK 全仓包含驱动、应用、构建、文档、设备树等目录。`drivers/` 是驱动实现，不是目标 API 定义或官方示例；全量索引该目录会显著增加解析、实体持久化和分段写入成本，却不能提升用法证据质量。

当前做法是按角色完整覆盖：`implementation` 取 `lib/`，`official_example` 取 `examples/`，`reference_project` 取 MTL 全仓，未覆盖顶层目录显式输出。这是性能与证据完整性的平衡，不应再把“全 Git 树”等同于“完整语料”。

### 挖掘阶段重复扫描调用

一次 `mine_patterns` 会先扫描调用构造序列，随后刷新特征树和聚类时再次分别扫描同一批调用；无结果时也会走同样的刷新分支。也就是同一档案、同一过滤口径下，`call_instances` 被重复读取多次。

应把首次扫描结果传给特征树和聚类刷新函数，或者让三者共享一次扫描后的内存行集，并按实际结果决定是否清理派生表。

### 标签归纳逐 API 查询

`induce_labels` 已批量预取参数形态和签名，但兄弟 API 仍按每个 API 单独调用 `related_apis`。每个查询都带作用域 CTE 和排序，在数万调用规模下会放大成大量重复扫描。

应增加批量兄弟 API 查询，一次取回当前模式涉及的全部 API，再在内存中分组。

### 档案上下文重复构造

`_profile_context` 会读取档案来源并重新计算来源指纹和来源提示。健康视图在一次调用中会分别给模式列表、聚类、证据、标签、分布等路径重复构造同一上下文。

应在一次读请求内复用已解析的档案上下文，并把来源身份计算限制在该请求需要的一次。

### 证据作用域条件绕过索引

证据查询用 `COALESCE(scope, caller_file || char(0) || caller)` 做分组和过滤。写入时已经持久化 `scope`，但该表达式会让 SQLite 难以直接使用作用域索引。随着语料增大，两阶段证据查询会变慢。

应优先使用持久化的 `scope` 列；只有历史空值才回退到拼接表达式。该优化不需要改变业务语义。

### 目标声明按来源重复加载

非实现来源解析时会从 `api_entities` 加载目标声明。当前每次 `index_repo` 都重新加载，且与前缀过滤无关地读取整批实体。若未来扩大到驱动级实现语料，实体数会成倍增加。

应按目标前缀在 SQL 层过滤，并允许一次索引运行内复用声明缓存，而不是按来源重复构造。

### 用法语料的分段写入非必需

非实现来源仍走完整的源码分段持久化与向量同步准备路径。用法挖掘只需要调用、样本和来源事实；如果这些来源不参与代码检索，分段写入属于非必要分支。

应为纯用法摄取提供显式开关，关闭分段写入和向量同步准备，只保留解析与调用持久化。

### 基线差分重复挖掘

解析覆盖差分会对同一版本的具名档案再次执行挖掘。基线差分用于审计，但不应在每次常规 e2e 中重复执行同样的派生计算。

应把基线差分设为显式选项，常规回放复用主运行的模式和健康结果；基线运行保留在周期性审计或夜间任务。

### 健康视图无界读取

健康统计以很大上限读取模式和聚类，再统一计算复用度与多样性。全量语料下这会加载不必要的派生行。

应让健康视图使用有限、可配置的采样或流式聚合，并在输出中注明统计范围。

## 非必要分支清单

- `minsup=1, minlen=1` 的无界序列枚举。
- 全仓驱动索引作为目标 API 定义来源。
- 同一批调用在模式、特征树、聚类中的多次扫描。
- 标签归纳中逐 API 的兄弟查询。
- 每读路径重复构造档案上下文和来源指纹。
- 用法来源的完整源码分段持久化与向量同步准备。
- 常规 e2e 中重复执行基线挖掘。
- 健康视图无界读取全部派生模式。

## 优化方向

按收益与风险排序：

1. 把有界挖掘参数和报告上限提升为生产配置，禁止默认无界模式枚举。
2. 合并调用扫描，复用档案上下文，批量化标签归纳查询。
3. 证据查询优先走持久化作用域索引。
4. 为纯用法摄取提供关闭分段写入的显式路径。
5. 按前缀过滤目标声明；仅在实现档案中持久化全量实体。
6. 将基线差分和全驱动实验改为显式、周期性任务。
7. 健康统计改为有界采样并声明口径。

## 性能测试补充方案

### 单元测试

在纯内存层增加规模对比测试，不依赖绝对耗时：

- 目标声明规模翻倍时，解析耗时的增长应保持在合理倍数内。
- 宏体片段解析在嵌套宏和条件宏样本上保持线性增长。
- 有界 PrefixSpan 在长序列输入下仍返回有限模式集。

测试只记录相对增长和时间中位数，避免把开发机绝对时间写死为断言。

### 集成测试

使用临时 SQLite 库和生成式夹具：

- 通过调用计数或轻量探针确认一次挖掘只扫描一次调用集。
- 通过查询计划确认证据作用域过滤走索引。
- 验证标签归纳只执行一次批量兄弟查询。
- 验证关闭分段写入后，用法来源仍保留调用、样本和来源事实。
- 验证健康视图的统计范围与输出说明一致。

### 端到端测试

在 `run_usage_mining_real.py` 中新增独立性能报告，按阶段记录：

- 语料 census 与文件数；
- 索引、解析、调用持久化、派生挖掘、标签归纳、证据、质量门槛的耗时；
- 调用数、实体数、模式数、数据库文件大小；
- 可选的峰值内存。

性能报告应作为审计数据而不是硬性失败条件；回归判定采用相对上一基线的倍数阈值，并把超阈值项标记为 `needs_review`。

### 周期性任务

以下实验不进入常规 e2e：

- DPDK `drivers/` 全量索引；
- `minsup=1` 无界挖掘；
- 完整 Git 工作树索引；
- 长时宏展开实验。

它们只在需要调整语料边界或容量规划时显式运行，并输出独立报告。

## 验收标准

- 常规完整角色语料回放稳定在分钟级，不使用无界挖掘参数。
- 一次挖掘对 `call_instances` 的扫描次数可反推且不重复。
- 标签归纳的兄弟查询次数与 API 数解耦。
- 证据查询的作用域过滤使用持久化索引。
- 性能报告能按阶段定位退化点，并区分数据规模增长和代码退化。
- 非必要分支有显式开关，默认不进入常规 e2e。
