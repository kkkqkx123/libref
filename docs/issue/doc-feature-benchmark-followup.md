# 文档特征基准剩余问题与下一阶段修复任务

本文基于冻结归档回放报告、判定集与漂移样本，以及相关生产代码路径，分析上一轮修复后仍未解决的观测问题。已完成的实体标签清理、判定集结构校验与三态指标分母不再列入。本文只做原因分析和任务拆解，不改代码、不改门禁、不改检索权重。

## 证据边界

| 证据 | 能说明什么 | 不能说明什么 |
|---|---|---|
| `tests/e2e/bench/outputs/retrieval-bench/doc-features/REPORT.md` | 派生计数、标签一致率、过滤命中率、排序差分与耗时总量 | 不能说明阶段耗时归属，也不能把离线替身的差分当成真实模型结论 |
| `tests/e2e/bench/data/bench.db` 只读统计 | 代码块、调用解析状态、模式数、覆盖行数与特征树关联规模 | 不能证明标签的语义正确性，标签仍来自同源派生证据 |
| 归档原始正文统计 | HTML 代码块是否带语言标记、Markdown 围栏是否有语言标签 | 不能替代人工判断示例是否真的调用目标 API |
| 单次本机回放 | 同机相对规模与瓶颈方向 | 不能跨机器比较绝对耗时，也不覆盖真实嵌入与向量后端 |

## 逐项原因分析

### 代码块语言证据缺失

`html_code_blocks` 只从 `pre` 或 `code` 的 `language-*`、`lang-*`、`data-lang` 属性取语言；`fenced_blocks` 只接受带配置语言标签的围栏。归档统计显示，`httpx`、`zod`、`jsoup`、`FluentValidation`、`Rocket` 的 HTML 分别有 205、1860、324、658、1651 个 `code` 标签，但没有任何语言属性；`fiber` 的 1520 个 `pre` 中有 1408 个带 `language-go`，因此得到 1409 个 snippets。`pydantic`、`gradle`、`vue` 的原始页是 Markdown，带标签围栏分别有 1355、3133、1398 个，对应 1265、1976、733 个 snippets。

这不是解析失败，而是归档站点没有留下语言事实。对齐模块在没有 snippet 调用时只能走限定名与短名词面匹配，因此这 5 站的 coverage、nodes 为 0 符合当前设计，不能靠降低置信度伪装成 AST 对齐成功。

### 已解析目标调用过少

`mine_patterns` 经 `_load_snippet_calls` 只取 `target_status=resolved_target` 的调用，再按 `sample_id` 分组，要求同一样本至少 2 次调用、`minsup>=2`、`minlen>=2`。只读统计如下：

| 站点 | snippet 调用 | `resolved_target` | 有解析调用的样本 | 其中调用数 ≥2 的样本 | 模式数 |
|---|---:|---:|---:|---:|---:|
| fiber | 1439 | 49 | 42 | 3 | 2 |
| vue | 1005 | 290 | 205 | 51 | 13 |
| pydantic | 4112 | 302 | 213 | 46 | 14 |
| gradle | 9942 | 718 | 568 | 110 | 24 |

大量 snippet 调用被标成 `not_target`（用户示例代码、内建调用或外部别名）是正确的归类，不应强行解析成目标 API。真正的问题是“可用于序列模式的样本”太少，且当前报告没有把 `snippets → 解析调用 → 有效样本 → 模式 → 覆盖` 的漏斗展开，导致覆盖稀疏只能从派生计数事后猜测。

### 漂移误报

`doc_facets` 用 `_DEPRECATED_WORDS` 做块级关键词扫描，`compare_consistency` 一旦看到 `deprecated` 标记就直接写 `drift`。人工标注的 7 条误报分别落在发布流程分类、安全基线、生命周期枚举和 changelog 泛化说明等语境：关键词确实出现，但修饰对象不是受跟踪的库 API。判定规则缺少“弃用对象是谁、替代项是什么”这层结构，因此把文本主题误当成 API 事实。

### 加权与排序

`_doc_feature_bonuses` 把示例块加 0.5、代码比例大于零加 0.25、废弃块减 0.5、对齐边按类型加 0.01–0.1，最后裁剪到 `[0,1]`；`capped_alpha` 在健康复用度为 0 时把权重压到 0.02。5 个无模式站点因此几乎没有加权空间；其余站点的加成也只是在融合分上做小幅乘法，难以改变 top-5 顺序。离线评测又使用 `BagOfTermsEmbedder`，语义题与中文题的候选池本身就不含真实向量信号，所以差分不能用来证明文档加权在生产中无效，也不能反向用来调参。

### 过滤命中率

`filter_by_doc_facets` 在融合后对候选 id 做硬集合交集，没有“过滤为空时回退”的分支。报告把 `hits / 全部题目` 当命中率，但题型分布决定了上限：`examples_only` 只对目标块为 example 的题目有意义，`exclude_deprecated` 必然影响以废弃块为目标的 drift 题，`aligned_only` 必然影响目标块没有实体边的 no_answer 题。当前数字更多反映题目构成，不能直接当作过滤器质量。

### 回放耗时

每个夹具依次做三件事：逐页抽取并摄取 snippet、按文档版本重跑 `mine_patterns`、整版重建该版本的所有文档派生表。`gradle` 有 260 页、1976 个 snippet、13588 个文档块和 103383 条特征行；`ingest_snippets` 每页都会注册来源并加载目标声明，`refresh_doc_features` 每次都删除并重写整版派生表。评测脚本只记录夹具总耗时，缺少阶段计时和调用次数，因而只能确认“大站慢”，不能确认是哪一阶段慢。

## 下一阶段修复任务

### 建立代码块语言证据分层

扩展代码块抽取的输入事实：除 `pre`/`code` 属性外，检查包裹元素的类、`data-*` 属性与紧邻说明文本，只有显式语言证据才登记为可解析 snippet；无证据的块单独计为 `unlabeled_code_block`。报告增加抽取漏斗，并把无 snippet 站点的 AST 对齐率明确标为不可测量。不得按站点生态猜测语言并计入评分。

### 展开模式挖掘漏斗并校准证据口径

在评测报告中加入 snippets、解析调用、`resolved_target`、有效样本、模式、覆盖六段计数。区分“库 API 用法模式”和“文档示例中的用户代码”，不要为凑覆盖把 `not_target` 改成目标调用。若确需放宽 `minsup` 或引入弱证据，必须按站点规模分别标定，并保留强证据列作为对照；不得全局下调阈值后直接写门禁。

### 改为有对象的漂移判定

把 `deprecated` 从布尔关键词标记升级为带证据对象的事实：弃用词所在句、候选实体或参数名、替代项。只有当句子能绑定到 `doc_api_links` 或 `api_entities` 中的受跟踪符号时才写 `drift`；生命周期枚举、安全基线、流程术语和泛化 changelog 写 `unknown` 或 `not_drift`。先用现有 40 条人工样本做回归，再扩样本；未达到阈值前仍只记录误报率。

### 给加权结论补归因再决定是否调优

保留 `doc_feature_alpha=0`，先增加逐查询的候选池位置、融合分、派生加成与最终名次记录，把“候选池外”“池内未进 top-k”“加权改变顺序”三类分开。再用真实嵌入链路重跑同一批题目，确认差分不是替身效应。只有在独立语义复核通过且区间显著后才讨论默认值与门禁。

### 重构过滤有效性指标

按目标文档的实际派生事实计算每个过滤器的合格题目集合：`examples_only` 取目标块为 example 的题，`exclude_deprecated` 取目标块未标废弃的题，`aligned_only` 取目标块有实体边的题。报告同时给出“合格题命中率”和“全体题保留率”，并列出被过滤掉的目标 URL。过滤器仍保持显式开关，不改成默认行为。

### 补阶段计时与批量化入口

在评测脚本中按阶段记录耗时与调用次数：代码抽取、snippet 摄取、模式挖掘、派生刷新、检索评测。`ingest_snippets` 的逐页调用先批量化目标声明加载；派生刷新先评估按变更文档增量更新的可行性。优化判定使用同机相对基线，绝对毫秒只用于说明量级。

### 明确节点标签的证据边界

把 14/270 作为覆盖事实写入报告口径，不在无父链的站点补造节点。若后续扩标注，只在已经存在完整父链的 `vue`、`pydantic`、`gradle` 等站点人工追加，并继续由结构校验测试约束实体点名与节点非空。

## 验收原则

- 每个新指标都能从报告追溯到原始事实，不使用同源派生值反推“真值”。
- 调优只在归因完成后进行；本阶段不写增益门禁、不修改 `doc_feature_alpha`、不修改漂移门禁阈值。
- 所有修复先补可复现计数或测试，再改生产逻辑；缺省路径不得用回退掩盖缺失证据。
