# 文档特征数据修复后的待分析项

依据：`docs/issue/doc-feature-benchmark-followup.md`、`docs/plan/doc-feature-e2e-improvements.md`、`docs/plan/doc-feature-manual-audit.md`、`docs/plan/doc-feature-completion.md`、`docs/plan/bench-followup-fixes.md`、`docs/plan/benchmark-failures-analysis.md`、`docs/plan/performance-bottlenecks.md`，以及冻结归档评测报告 `tests/e2e/bench/outputs/retrieval-bench/doc-features/REPORT.md`。本文只整理分析方向与证据边界，不改实现、不改权重、不冻结门禁。

## 一、数据修复结论

前两轮阻塞来自两类数据缺陷：代码块缺少语言证据，以及文档公开 API 名称无法桥接到源码内部实体。现在已分别补齐语言证据分层、片段级状态记录、源码导出别名事实与交互式导入恢复，并重建了基准数据集、重跑了文档特征评测。

五个原先零 snippet 的站点现在都有可解析片段和实体边；zod 从只有 2 条目标调用恢复到 925 条。所有站点都保留无标注、失败、歧义与非目标片段的逐条记录，因此“没有证据”和“有证据但不是目标 API”不再混在同一个计数里。

报告中的 nDCG 配对差分仍全部跨零，漂移抽检仍为 40 条样本、7 条误报。这些不是新代码可以直接消除的结论，需要下面的归因分析。

## 二、已解除阻塞的分析方向

### 对齐证据分层

现在可以按语言证据来源、片段解析状态和目标命中状态分层统计 `doc_api_links`。重点不是总体对齐率，而是强 AST 符号边、限定名边与名称模糊边的比例，以及它们分别落在哪些块类型上。需要抽样检查 `candidate`、`ancestor_class`、`block_tag` 三类语言证据产生的边是否真的指向题面点名的 API；`partial`、`ambiguous`、`non_target` 片段不应被折算成强证据。分析产出应为按站点与证据类型的边数、命中样例和误配样例，用来决定加权是否只消费强证据，而不是直接提高总体权重。

### 模式挖掘漏斗与站点阈值

六段漏斗已有可用数据：`snippets → calls → resolved_target → 有效样本 → patterns → coverage`。下一步应对每个站点统计有效样本长度分布、重复序列支持度、被语言候选误判的片段占比，并保留强证据列作为对照。若某个站点覆盖仍低，先判断是样本多样性不足、重复调用不足还是别名仍缺失；不得全局降低 `minsup`。分析结果若支持引入弱证据列，也应与强证据列并列报告，而不是覆盖原列。

### 特征树节点标签扩样

所有站点现在都有非空节点数，但题目侧节点标签只有 14/270。扩样应只在已有完整父链的文档块上做，优先从 vue、pydantic、gradle 中选取目标块，并按块特征、实体边和节点父链逐项确认。没有父链的站点继续标为不可测量，不补造节点。扩样结果仍需独立语义复核后才能用于门禁讨论。

### 有对象的漂移判定

现有 40 条漂移样本中自动 drift 35 条、误报 7 条。新的实体边为“弃用词指向哪个受跟踪 API、替代项是什么”提供了可回查对象。分析应以句子为边界，把 `deprecated`、`removed`、`replaced by` 等词与附近实体候选绑定，再与 `doc_api_links`、`api_entities` 对照。生命周期枚举、安全基线、发布流程和泛化 changelog 应写 `unknown` 或 `not_drift`。本方向先出误报样本清单和规则假设，不改漂移门禁阈值。

### 过滤有效性口径

当前报告的命中率分母是所有题目，低值主要反映题型分布，而不是过滤器失效。下一步按目标文档的实际派生事实计算合格题集合：`examples_only` 取目标块为 example 的题，`exclude_deprecated` 取目标块未标废弃的题，`aligned_only` 取目标块有实体边的题。报告同时给合格题命中率与全题保留率，并列出被过滤掉的目标 URL。过滤器仍保持显式开关。

### 检索加权的归因

九个站点的 nDCG 差分区间都跨零，当前只能维持 `doc_feature_alpha=0`。要做的是逐查询记录候选池位置、融合分、派生加成和最终名次，把“候选池外”“池内未进 top-k”“加权改变顺序”三类分开。离线替身没有真实语义向量能力，仍不能据此证明生产收益；若继续分析，必须与真实嵌入链路的结果分开呈现，不合并区间。

### 回放阶段归因

最新回放中 gradle 与 fiber 仍占主要耗时，但报告只有夹具级总耗时。后续先按代码抽取、片段摄取、模式挖掘、派生刷新、检索评测记录阶段耗时与调用次数，再判断是否值得批量化目标声明加载或改增量派生。优化判断使用同机相对基线，绝对耗时只说明量级。

### 判定集独立复核

270 条题目的结构检查、实体/节点/派生证据同源检查已通过，但这些标签仍来自归档正文与派生表。语义正确性需要独立复核，尤其关注无答案题是否真的没有目标 API、drift 题是否包含完整弃用句、题面与 facet 是否来自同一块。该分析不依赖新数据修复，却是写任何门禁前的必要条件。

## 三、分析顺序

1. 先做对齐证据分层与漏斗复核，确认新数据中没有用弱证据冒充强证据。
2. 再做漂移对象、过滤口径与节点扩样的样本分析，形成可人工复核的清单。
3. 然后补逐查询检索归因与阶段计时，分别解释排序差分和回放成本。
4. 最后在独立语义复核通过后讨论门禁；在此之前 `doc_feature_alpha` 保持 0，不写下限。

## 四、边界

- 所有分析只读冻结归档与重建后的数据集；需要新证据时显式重放，不在报告里手工补数。
- 不按站点生态猜测语言或 API，不把用户示例代码提升为目标调用。
- 真实模型端点、PostgreSQL 环境和人工复核意见属于外部条件，缺失时记为不可测量，不用离线替身结论替代。
- 本文列出的方向只定义分析输入、产出与判定边界；具体阈值、权重和门禁需等到归因完成后另行决定。
