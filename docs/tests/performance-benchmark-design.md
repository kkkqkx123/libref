# 性能基准测试设计：分层、口径与落地

本文只定义性能基准的验证方案，不新增业务实现。目标是让“索引是否变慢、检索是否变慢、规模增长是否失控、资源占用是否异常”有可复现、可归因、可与历史同机比较的答案；检索质量仍由 `docs/bench/` 负责，功能正确性仍由单元与集成测试负责。

## 一、现状判断

项目已有三类可用于性能判断的素材，但都没有形成性能基准：

| 现有资产 | 能回答什么 | 缺口 |
|---|---|---|
| `tests/e2e/bench/build.py` 的 `elapsed_ms` 与 `bench.json` 的 `max_build_ms` | 某次离线重建是否超出一次性预算 | 只有总耗时、没有阶段拆分；单次测量、没有重复与离散度；预算绑在机器实测值上，不能跨机比较 |
| `tests/e2e/bench/evaluate.py` / `sweep.py` 的耗时字段 | 一次评测或一次参数扫描花了多久 | 目的是质量实验，不是延迟分布；没有按查询的 p50/p95，也没有冷/热与并发口径 |
| `crates/simvec/benches/` 的 Criterion 基准 | 本地向量引擎的扫描、距离、HNSW、并发与持久化开销 | 只覆盖 Rust 原生层；Python 服务链路与数据库链路不在此列 |
| `services/infra/metrics.py`、`web/middleware.py` 的 `x-elapsed-ms` | 运行中进程的请求计数与近期延迟 | 是生产可观测性，不是受控输入；样本受线上流量与配额影响，且滚动窗口会被覆盖 |

另外，`docs/issue/api-usage-mining-performance.md` 已列出挖掘链路的具体热点（重复扫描调用、逐 API 兄弟查询、重复构造档案上下文、无界 PrefixSpan、健康视图无界读取等），但对应验证仍停留在设想。当前 `pyproject.toml` 没有性能标记，`tests/` 下也没有独立基准入口。

因此补充性能基准的原则是：**复用已有冻结语料与生产入口，在原模块上补计时与计数，不另建一套索引或检索实现，不把绝对毫秒写进单元测试断言。**

## 二、目标与非目标

性能基准只回答四个问题：

1. **回归**：同一台机器、同一夹具、同一配置下，一次改动是否让关键路径显著变慢。
2. **归因**：变慢发生在解析、落库、挖掘预处理、PrefixSpan、检索召回、融合还是出口层。
3. **伸缩**：语料或参数规模翻倍时，耗时增长是否符合该类算法的预期，而不是出现超线性跳变。
4. **容量**：在给定数据规模下，峰值内存、数据库体积与查询并发延迟是否仍可接受。

明确不做的事：

- 不替代检索质量门禁；质量指标与延迟必须分表报告，避免用“更快但更差”的结果互相抵消。
- 不引入 `pytest-benchmark` 到默认开发依赖。插件会带来额外锁文件变更与默认收集问题，而项目已有成熟的离线基准目录形态；用标准库计时加统一报告即可。原生向量层继续沿用现有 Criterion 基准。
- 不把真实网络、真实模型、Qdrant 服务、无界 `minsup=1` 实验或 DPDK 全仓索引放进默认档。
- 不为计时在生产响应体中新增字段，也不复制生产逻辑到基准里。归因优先用“同一输入下的分层计时 + 独立计数的审计轮”，而不是侵入业务代码。

## 三、分层与场景

### 1. 纯算法层

全部离线、可版本化夹具，在性能运行中默认包含，但不进入常规测试套件；目标是固定复杂度边界。

- `micro.prefixspan`：用固定随机种子生成序列库，规模取小、中、大三档，序列长度与字母表规模分别变化；只对有界参数跑常规档（`minsup` 取生产下界 2 或更高，`minlen`/`maxlen` 使用当前默认 2–10）。记录耗时、输出模式数、峰值追踪分配量，并验证“有界输入下模式数有限”。无界组合爆炸只作为显式容量场景，进入第四节的周期性档。
- `micro.chunking`：复用 `tests/fixtures/docs/sample.md` 扩展出的结构化正文，按篇幅倍数复制而非重写语义；覆盖标题路径、围栏、表格与 CJK 段落。记录耗时、块数、围栏平衡与空块数；块数不变量必须与功能测试一致。
- `micro.ast`：对每种语言选择一组固定大小的源码样本，走 `extract_file` 的生产入口；分别记首次解析（解析器与查询未缓存）和重复解析（缓存已热）。声明数、调用数与别名数为计数不变量；原生语法树内存不纳入 `tracemalloc`，只做报告说明。
- `micro.text`：查询整形、片段拼装与 CJK 展开的单次成本只在它们出现在检索热点时补充，避免一开始铺开过多低价值用例。

### 2. 存储与服务层

使用 `tests/e2e/bench/build.py` 生成的离线数据集，向量与重排沿用 `tests/e2e/bench/fakes.py` 的确定性替身；不使用真实 API。

- `store.fts_scope`：在单一版本、多版本、跨库全局三种作用域下调用 `fts_search`，记录 p50/p95 与命中数。另跑一轮独立的查询计划审计，确认作用域过滤走索引探测而不是结果集重排或全表扫描；审计轮开启 SQL 追踪，计时轮不开。
- `store.mining_scan`：围绕 `call_instances` 的加载与派生表清理做计数审计。一次 `mine_patterns` 当前会在主扫描与特征树、聚类、形态刷新里重复读取调用集；审计先记录真实次数，优化完成后再把“单次扫描”写成硬计数门禁。计数变化必须与模式数、节点数、簇数不变量一起看，防止“少扫了但结果也少了”。
- `service.retrieval`：对 `precise`、`balanced`、`thorough` 三种预设分别跑同一批固定查询。归因用差分：仅全文、全文加向量、加证据判定、加重排、加材料装配各自作为一行；若将来需要阶段内部耗时，只在基准侧包装注入的 `embed`、`rerank` 与 `vec_store`，不改服务返回契约。
- `service.insight`：挖掘读模型的 `patterns`、`evidence`、`tree`、`clusters`、`health` 是重复构造档案上下文的高发区。用固定版本与档案跑一轮读请求，记录次数与耗时；计数审计关注档案解析和来源指纹是否被重复计算。
- `service.graph_adjacency`：用冻结源码版本的热点实体跑固定邻域查询，分别测量 SQL 路径、快照冷构建与快照命中。计数审计核对事实表邻接读取次数，并把 SQL 与缓存结果逐项比对；命中档用相对 SQL 的加速比和冷构建回本批次数回答“是否默认启用缓存”，不把绝对毫秒写成门禁。

### 3. 管道层

不复制建库逻辑，在 `tests/e2e/bench/build.py` 原模块内补阶段计时，再由性能报告消费清单。

- `pipeline.docs_index`：按 `bench.json` 的文档夹具逐项记录解压、净化、分块、关键词抽取、落库、全文同步耗时。当前 `fiber/docs` 的分块耗时显著高于其他夹具，应作为关键词抽取改动的重点观察对象。
- `pipeline.code_index`：记录文件收集、语法解析、别名解析、实体与调用落库、源码分块耗时，并保留页数、文件数、实体数、调用数、解析失败数作为规模坐标。
- `pipeline.mining`：在已建库的数据集上按当前有界参数重新执行 `mine_patterns`，记录调用加载、序列构造、PrefixSpan、特征树、聚类、形态刷新与清理耗时；同时记录数据库文件增长量。

### 4. 出口与并发层

- `exit.web`：用 `httpx.ASGITransport` 直接请求 `build_web_app` 生成的进程内应用，覆盖 `/search`、`/read`、`/api-insight`、`/mining-health`。鉴权采用测试主体的确定性配置，关闭真实模型与外网。分别测单请求延迟和 1/4/16 并发下的吞吐；响应头的 `x-elapsed-ms` 只作为交叉校验，不作为唯一数据源。
- `exit.mcp`：在 Web 基线稳定后再补 stdio 入口的同类用例，重点是工具调用开销与载荷大小增长，不与 Web 共用延迟门禁。
- `native.simvec`：继续用现有 Criterion 基准，沿用其 `QUICK` 快档与完整档约定。Python 基准只记录调用向量后端前后的边界耗时，不重复测距离核与 HNSW 建图。

## 四、夹具、档位与环境

### 夹具来源

- 纯算法层用确定性生成器，种子写进规格；数据不入库，每次按规格重建。
- 管道与服务层只读 `tests/e2e/bench/fixtures/` 的冻结归档，复用 `archive.py` 的身份、配方比对和数据集修订；性能报告引用同一个修订，不另设标签机制。
- 出口层用同一数据集加进程内 HTTP 客户端；不启动监听端口，不连接真实外部服务。
- 无界 PrefixSpan、整棵驱动树索引、长时宏实验属于容量调查，默认不跑，结果只用于容量说明，不进入常规回归。

### 档位

| 档位 | 内容 | 触发方式 | 用途 |
|---|---|---|---|
| `smoke` | 纯算法小档 + 一个最小文档夹具 + 一次检索 | 本地显式运行 | 改动后的快速自检，秒级到分钟级 |
| `corpus` | 选定冻结夹具的完整索引、挖掘与检索 | 显式运行 | 发版前或性能改动后的正式比较 |
| `exit` | 单请求与并发请求 | 显式运行 | 出口层延迟与容量 |
| `capacity` | 无界/全仓/长时场景 | 显式运行，单独报告 | 容量规划，不设常规门禁 |

每档必须固定：Python 版本、平台与 CPU 摘要、核心数、设置快照（用 `redacted_dict`）、夹具修订、生成器种子、预热次数与重复次数。任一影响比较的字段变化，只生成观测报告，不与旧基线比较。

## 五、度量与判读口径

### 采样

- 墙钟用单调高精度计时器，CPU 时间单独记录；一次用例包含预热轮与测量轮，预热轮不进统计。
- 每个用例至少记录 7 个测量样本；报告给最小值、中位数、p95、最大值与变异系数。分位数采用最近秩口径，避免插值口径随实现变化。
- 冷启动与热路径分开：冷启动每次用新连接与新进程状态，热路径复用同一连接。无法可靠清理操作系统页缓存时不假装“绝对冷”，报告中标为“进程冷、系统缓存热”。
- 内存分两类：Python 对象分配用标准追踪器；进程峰值常驻内存需要单用例单独进程才有可归因性，否则只记录进程级上限。数据库体积按轮记录。两者只做趋势观察，不先设硬门禁。

### 计数不变量

下列量在独立的审计轮里统计，不计入计时轮：

- 一次挖掘对 `call_instances` 的扫描次数、派生表写入行数与清理行数。
- 标签归纳的兄弟 API 查询次数是否随 API 数线性增长。
- 一次读请求内档案解析与来源指纹计算次数。
- FTS 与证据查询的计划形态是否仍走预期索引。
- 输出行数、解析失败数与空块数等结构指标。

计数不一致属于硬失败；耗时变化属于软信号。两者不得混成一条“性能分数”。

### 基线与噪声

- 基线文件按机器与档位保存在忽略目录中，不入库；跨机器数字不比较。
- 回归阈值由同机基线自身的离散度确定：中位数比较的噪声带取基线变异系数的两倍与 10% 中的较大值；p95 因尾部更抖，下限取 20%。用例可在规格中收紧，但不得放宽到掩盖预期回归。
- 比值落在噪声带内记为“平手”，不据此改默认值。超过上界记 `needs_review`，低于下界记 `improved`。
- 伸缩用例额外比较规模翻倍后的耗时比；若超过规格给出的该类算法上界，即使单次耗时在噪声带内也要标记。
- 默认报告是建议性的。只有显式开启 `--enforce`，且基线存在、环境一致、计数不变量全部通过时，当前报告里标记为待复核的计时项才让命令返回失败。

## 六、报告与产物

每次运行写一份结构化报告，至少包含：

- 运行时间、代码提交标识、档位与命令参数；
- 环境摘要、脱敏设置快照、夹具修订与生成器种子；
- 每个用例的样本序列、统计值、计数不变量、内存与数据库体积；
- 与基线比较后的判定（改进、平手、待复核、不可比较）及原因；
- 未完成项与环境不可用项，不能用空结果冒充通过。

人类可读摘要与结构化报告取自同一次运行，避免两处口径分叉。产物落在忽略目录中；版本库只保留规格、脚本、说明与必要的计数门禁。

## 七、代码落点与实施顺序

新增目录只承担基准编排职责：

| 位置 | 职责 |
|---|---|
| `tests/e2e/perf/README.md` | 运行方式、档位、报告字段与基线维护约定 |
| `tests/e2e/perf/perf.json` | 用例、夹具、规模、参数、预热与重复次数、计数不变量、伸缩上界 |
| `tests/e2e/perf/harness.py` | 计时、统计、环境摘要、夹具生成、报告写出与基线比较，只有一份实现 |
| `tests/e2e/perf/run.py` | 命令行入口：按档位与用例运行、保存基线、比较报告 |
| `tests/e2e/perf/test_performance.py` | 显式开启的 pytest 门禁，只消费报告与计数结果，不重复计时 |

需要修改的现有位置：

- `pyproject.toml`：注册 `performance` 标记；不新增 Python 依赖。
- `.gitignore`：忽略性能报告与机器本地基线目录。
- `tests/e2e/README.md`：补一节指向性能基准目录与运行命令。
- `tests/e2e/bench/build.py`：在清单里补阶段耗时和结构计数；仍由原构建入口负责生成，性能脚本不另写建库流程。
- `tests/integration/test_retrieval_bench.py`：不改质量门禁；若需要引用构建耗时，只读清单字段。

实施按依赖顺序推进：先完成规格、运行器与报告；再补纯算法用例；随后把阶段计时并入原构建模块；再补检索与挖掘审计；最后补出口并发与显式 pytest 门禁。每一步都先能在 `smoke` 档产出完整报告，再扩到 `corpus` 档。

## 八、运行约定与验收

```bash
uv run python -m tests.e2e.perf.run --gear smoke
uv run python -m tests.e2e.perf.run --gear corpus --fixture httpx/docs --save-baseline
uv run python -m tests.e2e.perf.run --gear corpus --fixture httpx/docs --compare
LIBREF_RUN_PERF=1 uv run pytest tests/e2e/perf/test_performance.py -q
cargo bench -p simvec --bench distance_bench
```

验收标准：

- 默认测试套件不因新增基准变慢；性能用例默认跳过，显式开关才运行。
- 同一台机器、同一档位、同一夹具连续运行，报告字段完整，基线比较结论稳定；环境变化时明确标记不可比较。
- 每个热点用例都能从报告定位到阶段，而不是只有一条总耗时。
- 计数不变量对重复扫描、重复档案解析和查询计划退化给出明确失败原因。
- 无界挖掘与全仓实验只在 `capacity` 档出现，且不进入任何自动门禁。
- 原生向量基准继续由 Criterion 负责，Python 侧不复制其测量范围。
