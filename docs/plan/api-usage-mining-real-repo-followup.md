# 真实仓库用法挖掘结果复核与后续修复

本文记录对 `tests/e2e/outputs/usage_mining_real/` 的人工核查结论。当前链路已经证明真实仓库获取、固定提交、来源角色隔离、档案隔离、模式差分和证据导出可以运行，但结果仍偏“链路验证”，不能直接作为用法推荐依据。下一阶段应优先修复解析确认、档案内统计和展示口径，再扩大真实样本。

## 一、现有结果中符合预期的部分

- 三个语料源分别对应实现、官方示例与参考项目，commit、选择规则和目标过滤均有记录。
- 默认 `usage` 档案的来源集合只包含官方示例和参考项目，不包含实现来源。
- `dpdk-official-examples` 与 `dpdk-on-mtl` 拥有不同档案指纹，派生表互不覆盖。
- 差分报告体现了场景差异：官方示例偏 EAL 初始化、端口启停和收发包；MTL 偏原子操作、内存拷贝、外部内存与 DMA。
- 证据渲染带出了来源角色、来源键、样本身份与档案指纹。
- 实现档案中出现 `RTE_ETHDEV_LOG` 等内部宏调用，说明默认排除实现档案是必要的。

## 二、主要偏离

### 1. 具名档案建立在待审未解析调用上

真实仓库运行器显式放行待审调用，官方示例和 MTL 档案中的多数证据为 `AMBIGUOUS` 且 `resolve_kind=unresolved`。因此当前的 `rte_` 命中只是前缀候选，不是已经解析到目标版本实体的 API 事实。

后果：

- 默认 `usage` 档案为 0 组模式；
- 具名档案有模式，但主要依赖前缀匹配；
- 问答默认路径无法使用这些模式，人工放行口径也没有独立标记。

应明确区分“已解析目标 API”“前缀候选”“版本未确认”三类事实，不能只靠 `include_ambiguous` 绕过。

### 2. 健康统计不是档案内统计

两份健康输出中的置信分布、解析来源分布、未解析率和签名缺失率完全相同，说明这些指标仍按整个版本统计，而不是按当前档案的语料源过滤。只有新加入的调用形态分布和宏覆盖率是档案隔离的。

这会误导人工判断，例如把参考项目的解析噪声算到官方示例档案上。

### 3. 质量门槛检查过弱

`50-quality-gates.txt` 当前存在空泛通过：

- 调用存在只检查索引返回总数，未检查 `in_target_api=1` 的调用。
- 目标 API 只检查名称前缀，未检查解析命中目标实体。
- 默认档案排除实现，在默认档案模式数为 0 时天然成立。
- 健康门槛只检查字段存在，不检查比例或样本量。

下一阶段应改为按档案来源、调用事实和证据角色进行可证伪检查。

### 4. 版本兼容状态缺失

MTL 使用 `v23.12`，目标 DPDK 为 `v23.11`。当前输出没有记录参考项目声明的目标库版本，也没有把无法确认版本的调用标记为待确认。按设计，这类调用不应直接进入当前版本主分布。

### 5. 标签缺少来源提示

参考项目模式标签虽然有档案名和指纹，但没有明确的人类可读来源提示。标签内容也是固定占位文本，容易被误读为语义归纳或官方推荐。

### 6. 输出范围与摘要措辞不匹配

实际索引文件数为实现 2 个、官方示例 3 个、MTL 2 个，是受控切片，不是全仓生态验证。摘要尚未显著标明这一点。

### 7. 宏覆盖限制未在摘要中突出

官方示例档案宏覆盖率为 `2/236`，MTL 档案为 `0/549`。DPDK 是宏密集库，该数字说明当前选择集合和解析能力覆盖不足，应作为限制写入摘要和质量门槛，而不只留在健康明细中。

### 8. 证据定位缺少规范 URL

来源地址是本地 checkout 路径，证据文件是相对路径。人工核查无法直接跳转到 GitHub 上对应 commit 的具体行。

## 三、修改方案

### 阶段一：档案内健康统计

- 健康视图中的置信分布、解析来源分布和质量比例全部按档案 source_ids 过滤。
- `macro_coverage` 与调用形态分布沿用同一来源集合。
- 输出中同屏比较不同档案的未解析率，避免全局数字混入档案结论。

### 阶段二：目标命中状态分层

- 扩展调用实例的目标状态表达：已解析命中、前缀候选、版本未确认。
- 前缀候选不静默视为已解析目标 API。
- 具名真实档案输出中分别统计三类数量。
- 默认 `usage` 档案保持待审排除；具名审查档案如放行前缀候选，必须在输出中显式标注。

### 阶段三：强化质量门槛

质量检查改为至少覆盖：

- 每个档案的 source_ids 非空且互不误用；
- `in_target_api=1` 的调用数大于零，且来自档案允许的角色；
- 默认 usage 证据不出现实现角色；
- 具名档案证据只出现声明的角色；
- 未解析比例与前缀候选比例写入检查报告，超出阈值时标记 `needs_review`，不直接判失败；
- 档案指纹与来源指纹一致，来源规则变化后指纹必须变化。

### 阶段四：版本兼容与来源提示

- 在真实仓库输入中记录参考项目声明的目标库版本。
- 输出版本兼容状态；无法确认时标为未确认，不猜测兼容。
- 参考项目标签和答案提示块增加仓库名、tag、commit、来源角色与非官方推荐提示。
- 标签渲染若是确定性占位文本，应明确标注为审查样本而非语义标签质量证明。

### 阶段五：证据定位与摘要口径

- 为每条证据生成基于 commit 的规范 URL，包含仓库相对路径和行号。
- `SUMMARY.txt` 明确写出受控文件切片、文件数、未覆盖目录和宏覆盖限制。
- `50-quality-gates.txt` 加入宏覆盖率摘要和未解析比例摘要。
- 将“完整仓库验证”改称“固定提交的受控真实切片验证”，除非后续显式扩大文件选择。

### 阶段六：解析覆盖增强

- 扩大目标库头文件选择，覆盖函数原型、static inline 和常用宏定义。
- 对 DPDK 函数式宏记录宏体可见调用，不尝试完整预处理展开。
- 对比增强前后的未解析率、前缀候选率和模式集合，形成差分报告。

## 四、需要人工审核的问题

1. 前缀候选是否允许进入具名审查档案？若允许，是否必须另有审批记录？
2. 默认 `usage` 档案目前为空，是接受“没有可确认用法”，还是应引入显式批准的候选调用？
3. MTL `v23.12` 与 DPDK `v23.11` 是否视为版本兼容？依据应来自 MTL 依赖声明还是人工确认？
4. 参考项目模式是否允许进入问答材料？若允许，来源提示应放在标签、证据还是两者都放？
5. 真实仓库输出是继续作为受控切片，还是扩大到完整目录并接受更长的运行时间？
6. 未解析比例阈值定为多少：超过多少只警告，超过多少需要人工审核？
7. 宏覆盖率低时，是把缺口写入健康统计即可，还是要阻止模式进入默认问答？

## 五、重跑 e2e 的验证标准

### 命令

```bash
uv run python tests/e2e/sync_usage_repos.py
uv run python tests/e2e/run_usage_mining_real.py \
  --out-dir tests/e2e/outputs/usage_mining_real
LIBREF_RUN_E2E=1 uv run pytest -q tests/e2e/test_usage_mining_real.py
```

网络不可用时同步脚本按环境不可用退出，不作为回归。仓库已存在时复用固定 checkout。

### 输出完整性

重跑后必须存在：

- `00-manifest.txt`
- `01-sources.txt`
- `02-profiles.txt`
- 四组模式文件
- 两组差分/证据文件
- 两组健康与标签文件
- `50-quality-gates.txt`
- `SUMMARY.txt`

若新增版本兼容与规范 URL 输出，还应出现独立报告或并入上述文件的明确字段。

### 通过标准

- 三个语料源的角色、commit、选择规则与目标过滤可辨认。
- 默认 `usage` 档案的 source_ids 不含实现来源。
- 两个具名档案的 source_ids 各自只含声明角色。
- 所有档案指纹在来源规则不变时稳定，规则变化后改变。
- 质量门槛检查不再出现空泛通过，布尔项必须可由输出数据反推。
- 健康统计的置信分布与解析来源分布在不同档案之间可以不同，且只统计该档案来源。
- 证据带 `source_role`、`sample_id`、`profile_fingerprint` 和基于 commit 的规范 URL。
- 摘要明确列出文件切片范围、未解析比例和宏覆盖限制。
- 参考项目标签或答案提示带可辨认的非官方来源标记。
- 新增或修改的差分用例必须能反映“实现档案模式不进入默认 usage 档案”。

### 不通过的情形

- 任一输出缺失或为空且没有跳过说明。
- 默认 usage 档案包含实现来源或实现角色证据。
- 不同档案健康统计完全一致且未按来源过滤。
- 前缀候选被静默标为已解析目标 API。
- 版本不一致或未确认调用直接进入默认 usage 主分布。
- 标签未绑定档案指纹。
- 测试仅因网络失败跳过，却声称真实仓库验证通过。

## 六、完成定义

下一阶段完成的条件是：

1. 上述阶段一到阶段五全部落地并通过检查。
2. 阶段六给出差分结果，明确解析覆盖提升或说明仍未覆盖的部分。
3. 需要人工审核的问题已有结论，且结论反映到 fixture、输出说明和 e2e 断言中。
4. 重跑 e2e 后，`SUMMARY.txt` 与 `50-quality-gates.txt` 可被人工逐项反推，不再依赖“全为真”的空泛结论。
