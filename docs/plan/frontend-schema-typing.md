# 前端 API 类型契约收紧

> 范围：`webui/src/api/schema.d.ts` 的生成链路与消费方。目标是把“能编译但会静默取错字段”的
> 契约收紧为“字段拼错即编译失败”，并保持后端 Pydantic 模型是唯一事实来源。
> 本目录总览 `README.md` 已引用本文。

## 生成链路与原则

契约由 `src/libref/web/api.py` 的 Pydantic 模型与 `src/libref/web/app.py` 的路由签名生成，
经 `tools/export_openapi.py` 导出为 `webui/openapi.snapshot.json`，再由 `openapi-typescript`
生成 `webui/src/api/schema.d.ts`。生成物不手改；所有收紧先从后端模型开始，再重新生成，
前端只做派生类型与消费方适配。

## 当前覆盖与问题

生成物覆盖后端全部 REST 能力：44 条路径、51 个操作、115 个 schema，前端调用其中 45 个操作。
未接入的四个操作是独立图查询、单请求查询、链接统计与按主体批量撤钥，属于 UI 排期问题，不是契约缺项。
CLI、MCP 工具与登录流程不在 HTTP 契约范围内。

问题集中在三处：

- 五个洞察接口把不同视图的行统一成 `JsonValue` 字典，前端只能猜测字段名，已出现读取
  `callee_name` 而后端输出 `callee` 的错配；
- 入库请求的 `params` 与任务参数是通用 JSON 字典，前端用 `String`、`Number`、`Boolean`
  逐字段还原；
- 部分已有封闭取值域的字段仍是 `string`，列表查询状态与响应状态不一致。

`api/client.ts` 已从 `paths` 推导路径、方法、查询、请求体与响应类型，这部分不需要重做。

## 任务一：洞察行结构化

为五个洞察接口的每个视图建立 Pydantic 行模型，字段来自服务层实际输出；自由形态数据
（参数、签名参数、证据调用实参）仍保留 `JsonValue`。响应信封增加 `view` 字段，并让同一
接口内不同行形状对应不同的字面量取值，使生成的 TypeScript 联合可以按 `view` 窄化。

前端以 `view` 判断后取得具体行类型；通用列表与证据组件接受行类型联合，通过统一取值函数
读取动态列。洞察页的字段跳转改为类型守卫，不再依赖猜测的键名别名。

## 任务二：请求参数结构化

入库请求详情的 `params` 直接复用入库请求模型。前端“按原参数重提”不再逐字段转换，
而是把已结构化参数与表单字段对齐。任务详情的 `result` 保留 `JsonValue`，因为它由不同
任务产出，属于真正的自由形态数据。

## 任务三：封闭取值域

答案置信度收窄为后端实际产出的 high 与 low；入库请求列表与反馈列表的 `status` 查询参数
复用响应侧已有的状态联合。任务种类保持开放字符串：运维可直接提交新种类，已有契约测试
也依赖该扩展点；错误码保持开放字符串，因为存在 `http_<状态码>` 动态回落。

## 任务四：边界适配

错误体解析继续以 `error` 是否为字符串作为判据，避免把任意 JSON 当作错误对象。查询串中的
多值参数继续采用逗号串编码，因为它同时是深链地址格式；不在本轮改成重复查询参数。
时间字段维持现有双表示：密钥创建使用 Unix 时间戳，其余时间使用字符串，配额重置字段
沿用历史数值兼容；统一表示需要同时调整配额、契约测试与客户端格式化，收益不足以在本轮承担。

## 验收

- 后端：新增契约测试断言洞察响应信封包含 `view`，且每个变体的 `items` 指向命名行 schema；
  现有全部路由仍满足命名响应模型与严格字段约束。
- 前端：生成物漂移检查通过；`vue-tsc` 能拦截洞察行字段名错误与请求参数字段漂移。
- 命令：`uv run pytest`、`uv run ruff check src tests`、`uv run ruff format --check src tests`、
  `uv run mypy src`、`cd webui && npm run gen:api && npm run check && npm run build`。

## 落地记录

后端为五个洞察接口补齐了按视图分组的行模型，响应信封新增 `view` 并指向命名行 schema；
自由形态的调用实参、签名参数与任务结果仍保留 `JsonValue`。前端按生成类型声明各页行数组，
通用表格与证据组件保留按列名取值的能力，页面跳转改用后端实际输出的字段名，
其中模式证据从 `calls` 取首个 `callee`，不再读不存在的 `callee_name`。

入库请求详情没有直接复用请求模型：服务层会归一化参数，去掉 `kind` 并补上解析来源、
确认标记与请求标识，因此单独定义 `IndexRequestParams`，既有字段全部显式声明。
前端重提表单改为按结构化参数赋值，并继续用请求详情的 `kind` 判定仓库或文档类型。

答案置信度与两处列表状态查询已收窄。任务种类、动态错误码、历史时间表示与逗号串多值参数随后按 `frontend-wire-contract.md`
单独实施完毕，本文件不再维护这四项的细节。
契约测试新增洞察响应判别字段与行 schema 断言，并复核了参数模型、置信度枚举与全部路由的
命名响应模型。带真实调用行的用例覆盖证据、片段、调用与参数四个视图；它同时暴露了调用查询
在连表后 `ORDER BY id` 的列名歧义，已改为限定到 `call_instances.id`，排序语义不变。

验证结果：`pytest` 全绿；`ruff`、`ruff format --check`、`mypy` 全绿；
`npm run check`（类型、契约漂移、词条、令牌）与 `npm run build` 均通过。
