# 前端功能覆盖与样式一致性核查（2026-11-18）

> 范围：`webui/` 前端。以 `docs/plan/frontend/` 规划文档为需求基准，以 `src/libref/web/app.py`
> 的 REST 端点为能力上限，逐项核对代码事实。本文记录核查发现、设计决策与修改方案。
> 核查方法：全量读取路由表、API 客户端、17 个视图与 13 个共用组件，并对样式块、
> 检查脚本、词条引用做全仓文本扫描。所有结论附 `file:line` 引述。
> 状态：§11 的五项决策已于 2026-11-18 拍板并落入三批次代码改动；
> 各批次实际改动与验证结果见 §12。

- 规范约束：`AGENTS.md:15-19`（代码英文、`docs/` 简体中文）、

## 1. 结论摘要

- 功能覆盖：六功能域中五域完整落地，源码洞察域有一处实质缺口（`/repo-deps`），
  另有一处规划模糊项（`/link-stats`）未落地。详见 §3、§4。
- 功能完整性：核心检索、问答、阅读、洞察、入库、任务、审核、反馈、管理的
  主链路均已接通后端并有深链、降级、配额闭环；缺口是边缘附属能力，
  不影响主流程可用。详见 §5。
- 样式一致性：CSS 文件来源本身是单一的（全局 `tokens.css` + 组件 `<style scoped>`，
  无第二个样式入口），共用组件未出现多源覆盖。但**令牌纪律未兑现**：
  规范要求的"字号、间距出自令牌"在代码中大面积写死，且门禁脚本不检查这些值。
  详见 §6、§7、§8。

## 3. 缺口一：`/repo-deps` 依赖区块（P1，规划与实现矛盾）

**事实**。

- 后端提供 `GET /repo-deps`（`src/libref/web/app.py:1379`）。
- 规划明确要求该能力：功能域表把 `/repo-deps` 列入源码洞察域
  （`docs/plan/frontend/README.md:20`），端点表要求"版本详情附属"
  （`docs/plan/frontend/api-mapping.md:18`），页面清单要求仓库目标解析后
  附依赖区块（`docs/plan/frontend/pages.md:79-80`）。
- 剩余任务文档声称已落地：`docs/plan/frontend/remaining-tasks.md:130` 写
  "仓库目标在解析结果处附依赖区块（`/repo-deps`）"，`:168` 落地结果表写
  "入库向导补三个发现入口、探测参数……与依赖区块"。
- 但代码事实相反：前端全仓（含所有 `.vue`/`.ts`）无任何 `/repo-deps` 调用、
  无依赖区块渲染、无相关标识符。仅存在 4 个孤儿词条——
  `webui/src/i18n/locales/zh-CN.ts:450-453`（`depsTitle`/`loadDeps`/`depsEmpty`/`depsFailed`）
  与 `webui/src/i18n/locales/en.ts:450-453` 对应项。`IngestWizardView.vue`
  的发现入口在 `:49-55`、`:209-227`，均无依赖加载逻辑。
- 即规划出现了"只加词条、未接 API 与 UI"的半落地，且 `pages.md:80` 又写
  "暂未迁移"，同一份规划集内部自相矛盾。

**影响**。用户在入库向导解析到仓库地址后无法查看其依赖构成，与
  "源码洞察"功能域承诺不一致；4 个词条成为死数据，误导后续维护者以为已实现。

**备选**。

- A：在 `IngestWizardView` 仓库解析结果处增加依赖区块，调 `/repo-deps`，
  复用现有 4 个词条，处理 404/502。
- B：承认不做——删除 4 个孤儿词条，修正 `README.md:20`、`api-mapping.md:18`、
  `remaining-tasks.md:130,168` 的表述为"未实现/延后"，与 `pages.md:80` 对齐。
- C：移到洞察域——在 CatalogView 版本详情处加依赖入口，不进入库向导。

**决策：C（原备选 C，即 §11.1 的决策 A 补全 + 位置改到目录页）**。
  关键依据：`/repo-deps` 的 SQL 只查 `repo_dependencies` 表中**已入库**版本
  （`repo_source.py:96-128`），而向导 step 0 解析的是待入库目标（`form.name`），
  该目标此时无依赖记录，放在向导里必然查空。CatalogView 的版本行才是
  `api-mapping.md:18` 定义的"版本详情附属"，且 library/version/ecosystem 三者齐备。
  词条从 ingest 组（原 `zh-CN.ts:450-453`）迁入 catalog 组并接入真实 UI。
  落地见 §12 批次一。

## 4. 缺口二：`/link-stats` 引用统计（P3，规划模糊）

**事实**。

- 后端提供 `GET /link-stats`（`src/libref/web/app.py:1435`）。
- 规划把它列为"阅读器附属"（`docs/plan/frontend/api-mapping.md:19`），
  但 `pages.md` 的阅读器章节（`:24-29`）未把统计纳入必需控件。
- 前端无任何 `/link-stats` 调用，也无相关词条或 UI。
- 对比 `/repo-deps`：此项连词条都未加，属"规划提及但从未开工"，
  与上一项的"半落地"性质不同。

**影响**。低。文档承诺的"热门引用/单页统计"能力不可用，但因未列入页面必需控件，
  不构成主链路缺口。

**备选**。A 补进 ReaderView 作为附属信息区；B 明确延后并从
  `api-mapping.md:19` 移入"后续项"章节，避免长期挂在能力表内造成误读。

**决策：B（延后）**。后端能力保留，前端本轮不实现；把 `api-mapping.md:19`
  从主能力表移入"后续项"，消除长期误读。见 §11.2、§12 批次三。

## 6. 样式来源结构：单一，无多源冲突

就"共用组件是否正确使用单一 CSS 来源"这一具体问题，核查结论是**正确**：

- 全局样式入口唯一：`webui/src/main.ts:2-4` 依次引入
  `element-plus/dist/index.css`、暗色 `css-vars.css`、`./styles/tokens.css`，
  无第二个自定义样式入口。
- 13 个共用组件全部使用 `<style scoped>`（如 `PageHeader.vue:17`、
  `HealthDot.vue:16`、`DegradedBanner.vue:39`），无组件私自 import 额外
  CSS/SCSS 文件，无同名类跨文件覆盖。
- 通用工具类（`.libref-page`/`.libref-card`/`.libref-muted`/`.libref-mono`/
  `.libref-ellipsis`）集中定义在 `tokens.css:82-111`，被视图与组件广泛复用
  （如 `SearchView.vue:2`、`CitationCard.vue:3-4`、`EvidenceList.vue:9-10`）。
- 语义色通过令牌间接使用：`StatusBadge.vue:17-23` 把状态映射到 Element Plus
  的 `el-tag` type，`HealthDot.vue:24-30` 用 `var(--semantic-*)`，
  均未写死色值。

**判定**：不存在"同一组件样式分散到多个 CSS 文件"或多源覆盖问题。
  样式来源的组织结构是健康的；问题在纪律执行（§7、§8），不在来源数量。

## 7. 问题一：字号与间距未令牌化，规范与实现系统性偏差（P2）

**事实**。

- 规范要求："所有颜色、字号、间距只出自令牌文件，页面与组件内禁止写死
  色值字号"（`docs/plan/frontend/style-guide.md:11`）。
- 但令牌文件 `tokens.css` 只定义了 brand/semantic/confidence/surface/text/
  border 色值与 `--radius-small/base`、阴影（`:6-53`），
  **没有任何字号、间距令牌**（grep `--spacing`/`--font*` 结果为 0）。
- 连令牌文件自身的工具类也写死：`.libref-page` 的 `padding: 20px`
  （`tokens.css:83`）、`.libref-card` 的 `padding: 16px`（`:93`）、
  `.libref-muted` 的 `font-size: 13px`（`:99`）、`.libref-mono` 的
  `font-size: 12px`（`:104`）。
- 组件与视图沿用写死值，全仓 scoped 块中 `font-size` 硬编码 8 处：
  `KeyIssueDialog.vue:100,106`（12px）、`SearchResultList.vue:61`（14px）、
  `AppHeader.vue:86`（18px）、`PageHeader.vue:27`（20px）、
  `HealthDot.vue:21`（13px）、`AdminView.vue:457`（12px）、
  `ReaderView.vue:247`（14px）。
- 间距（`gap`/`margin`/`padding`）写死更为普遍，遍布多数组件与视图，
  例如 `PageHeader.vue:22-23` 的 `gap:16px`/`margin-bottom:16px`、
  `EvidenceList.vue:4-7` 的 `gap:8px`/`padding:8px 0`。
- 另有内联 `style="width: …"` 约 40 处（如 `CatalogView.vue:7,18,49`、
  `ReaderView.vue:7,17,20,23`），宽度未按任何令牌或 class 收敛。

**影响**。色值做到了单源，但字号/间距/宽度各自为政：调整全局字阶或间距节奏
  需要逐文件改，深色模式与紧凑模式无从统一；规范第 11 行处于"写了但没执行"
  状态，随页面增加持续劣化。

**备选**。

- A：全量令牌化——新增字号/间距/宽度令牌，改造全部视图与组件的写死值，
  并扩展门禁脚本覆盖。改动面大（约 20 个文件、数十处），但一次性兑现规范。
- B：收窄规范——承认字号/间距用绝对 px 是可接受的实现细节，把
  `style-guide.md:11` 改为"颜色必须出自令牌；字号间距用固定 px 即可"，
  并把门禁脚本现状固化为契约。改动小，但等于放弃全局排版一致性。
- C：分层令牌——只令牌化高频重复的字阶（如 12/13/14/18/20px）与间距档
  （4/8/12/16px），全量替换；内联宽度改用少量语义 class。折中方案。

**决策：C（分层令牌化）**。新增高频字阶（12/13/14/18/20px）与间距档
  （4/8/12/16/20px）令牌，替换全部写死值与内联宽度，扩展门禁。见 §11.3、
  §12 批次二。

## 8. 问题二：门禁脚本覆盖不足，无法阻止样式漂移（P2）

**事实**。`webui/scripts/check-design-tokens.mjs` 的全量逻辑：

- 只校验 `REQUIRED` 列出的 13 个令牌在 `:root` 与 `.dark` 同时存在（`:11-44`），
  以及 `--el-color-primary` 映射存在（`:46-48`）。
- 色值扫描用 `HEX = /#[0-9a-fA-F]{3,8}\b/g`（`:50`），只匹配十六进制，
  不识别 `rgba()`/`hsl()`/具名色。
- 扫描只 `walk` 到 `components/` 与 `views/`（`:65-66`），
  **漏掉 `src/App.vue`、`src/styles/` 自身与 `src/` 根级文件**。
- 不检查内联 `style=` 属性，不检查 `font-size`/间距/宽度，不检查同一选择器
  是否在多文件重复定义。

**影响**。这正是 §7 偏差能通过 `npm run check` 的原因：门禁锁住了色值单源，
  却对字号/间距/内联宽度完全放行；`docs/plan/frontend/style-guide.md:23`
  承诺的"三方对齐、漂移即失败"只对最小集成立。

**备选**。

- A：扩展脚本——扫描范围扩到整个 `src/`，增加字号/间距/内联 style 检查，
  并把扫描类别配成清单。注意：若 §7 选 B（不改代码），脚本不应扩大检查范围，
  否则门禁立刻失败；两者需配套。
- B：保持脚本现状，在 `style-guide.md` 写明门禁只覆盖色值与必需令牌，
  避免文档夸大。

**决策：A（扩展门禁）**。扫描范围扩到整个 `src/`（含 `App.vue`），
  增加字号、间距、内联 `style` 检查，并校验令牌文件自身的工具类也不写死值。
  与 §7 的 C 决策配套。见 §12 批次二。

## 9. 问题三：共用元素样式重复定义（P3）

**事实**。少数共用视觉元素在多个文件各写一遍，未抽取到单一位置：

- 无序列表缩进样式 `margin: 4px 0 0; padding-left: 18px;` 同时出现在
  `DegradedBanner.vue:44-45`（`.libref-degraded-list`）与
  `ReaderView.vue` 的 `.libref-reader-candidates ul`。
- 卡片表面 `background: var(--surface-card)` 在 `AppHeader.vue:82` 与
  `AppSidebar.vue:60` 各写一次（值一致、来源一致，仅为重复而非冲突）。
- 这些是"样式来源单一但定义重复"，与 §6 的多源冲突是不同性质的问题。

**影响**。低。值来自令牌，不会出现颜色漂移；但新增同类元素时容易漏改一处，
  造成列表缩进/卡片内边距不齐。

**备选**。A 把列表/卡片高频组合抽为令牌文件里的共享 class 或工具类；
  B 维持现状，仅在新增同类元素时人工对齐。

**决策：A（抽取共享类）**。优先级低于 §3 与 §7，放在批次三顺带完成。
  见 §11.5、§12 批次三。

## 10. 修改方案与批次

按依赖与风险排序，分三批；每批结束按 `AGENTS.md:92-100` 收敛验证。

- 批次一（功能缺口，P1）：在 CatalogView 版本详情补 `/repo-deps` 依赖对话框，
  复用并按决策迁移 4 个 deps 词条，处理 404/502；不动后端。
  验收：目录页版本行可见依赖入口，列表展示 ecosystem/name/req/source_file，词条不再是死数据。
- 批次二（令牌与门禁，P2）：新增字阶/间距/宽度令牌，替换组件与视图写死值与内联样式，
  扩展 `check-design-tokens` 门禁并更新 `style-guide.md`。
  验收：`npm run check` 通过且门禁能拦住写死值。
- 批次三（收尾，P3）：把 `/link-stats` 从能力表移入后续项，抽取共享列表/卡片样式类。

每批验证（来自 `AGENTS.md:92-100`、`webui/README.md:17-30`）：

```bash
uv run pytest -q
cd webui && npm run check && npm run build
```
