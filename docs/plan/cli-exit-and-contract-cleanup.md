# 出口边界与契约收口设计

## 背景

当前三服务端出口（本机 CLI、MCP、Web）与调用方客户端 `librefctl` 的职责划分已经成立：本机 CLI 直接触达主机资源，MCP 面向模型，Web 提供 HTTP 契约，`librefctl` 只经 HTTP 调用 Web。现存问题集中在三处：

- `librefctl` 位于 `packages/`，与前端 `node_modules` 的包目录语义混淆，且独立发行目录不应藏在该名下。
- `serve-mcp` 与 `serve --stdio` 是两条 stdio 启动路径，一条不构造运行时上下文，另一条不共用指纹校验和退出排空，启动行为发生分叉。
- 同一服务的输出字段、工具数量、错误码和配置字段在多份契约中手工维护，已出现 Web 搜索缺少 `cross_lingual`、MCP 工具数文档落后、配置文档漏字段等问题。

## 决策

- `librefctl` 作为独立 uv workspace 成员迁移到项目根目录的 `librefctl/`，源码仍在成员内的 `src/librefctl/`。服务端发行包不拥有客户端模块，客户端也不导入 `libref`；不保留旧路径。
- 所有 stdio MCP 启动统一到一个组装函数。无论从 `serve-mcp` 还是 `serve --stdio` 进入，都使用相同的设置快照、运行时上下文、启动校验、配置指纹校验和退出排空。stdio 没有监听主机，启动校验按回环处理。
- Web 搜索与 MCP 搜索共享同一组检索状态字段；Web 响应模型显式携带 `cross_lingual`。
- 删除已退役且无消费者的 `mcp_host`、`mcp_port` 配置字段，清理示例配置和相关测试。配置文档以当前 `LibrefSettings` 为准补齐向量调优与存储后端字段，并把实际密钥字段列入环境约束。
- `librefctl` 继续只覆盖调用方和 operator 所需的 Web 路由。UI 专属的 `/metrics`、`/readyz`、页面列表，以及配额策略与配置刷新管理接口不进入客户端，边界由应用文档明确说明，调用方通过 Web API 直接使用。

## 任务顺序

1. 迁移发行目录：移动客户端源码、包配置与说明，更新 workspace、源码路径、lint 与类型检查路径、文档路径和锁文件；删除 `packages/librefctl` 空目录。
2. 合并 stdio 启动路径：在服务端 CLI 中建立唯一的 stdio 组装入口，两个命令只做参数解析并委托给它；补一条入口一致性测试。
3. 对齐检索状态：Web 搜索响应加入 `cross_lingual`，补 Web 与 MCP 搜索结果字段的差分测试。
4. 清理配置契约：删除失效配置字段及示例，补齐配置文档字段表、校验规则和密钥清单，更新受影响的单元测试。
5. 同步应用文档：修正 MCP 工具数与错误码、`doc_insight` 说明，补齐 Web 管理/进程接口说明，说明客户端能力边界与新的源码位置。
6. 收尾验证：一次性运行格式、lint、类型检查与全量测试；检查仓库内不再出现旧目录引用。

## 验证口径

- 客户端命令仍按 Web 路由做参数级差分；MCP 与 Web 的搜索状态字段一致。
- 两个 stdio 入口走同一个组装函数，服务端 CLI 仍不暴露调用方检索命令。
- 配置文件不再接受已退役字段；示例配置能加载。
- 文档中的路径、工具数、错误码和字段表与代码一致。
- 不新增兼容别名，不保留旧目录，不升级任何版本号。
