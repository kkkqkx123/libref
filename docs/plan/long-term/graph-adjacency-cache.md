# 图查询派生邻接缓存设计

> 位置：`docs/plan/long-term/` 长效设计。针对图查询在有界预算内仍需大量重复事实表读取的性能问题；目标是减少热版本上的邻接查找成本，同时保持查询结果与现有 SQL 路径完全一致。

## 1. 背景与目标

当前图遍历按节点展开邻域：每访问一个 API、文档、簇或特征节点，都会向事实表发出数条查询。`graph_query_budget` 已经给出单次查询的硬边界，边界内不会无限扩张；但在两跳邻域和高频调用场景下，成本仍集中在重复的 B-tree 查找，而不是结果组装。

目标是给只读图视图增加一层可重建的进程内邻接快照，让同一版本、profile 与租户上的多次查询复用边结构。缓存只保存派生结构，不成为事实源；任何缓存失效或构建失败都必须回到现有 SQL 路径，不能以截断真相代替回退。

## 2. 触发条件与非目标

启动条件是基准显示邻接 SQL 占图查询尾延迟的主要部分，并且 gold 用例已经稳定。没有测量结论前不引入缓存。

非目标包括：不引入图数据库，不持久化邻接表到业务表，不改变五种查询形态的语义，不参与 FTS/向量排序，不引入 LLM 关系抽取，也不把缓存命中率作为正确性指标。

## 3. 归属边界

`store/graph.py` 继续作为唯一图查询面，服务层与三个出口不感知缓存。若缓存逻辑独立成文件，只放在 `store` 包内，职责限定为“派生邻接快照”，不得替代或包裹 `GraphView` 成为第二查询入口。

边的派生规则仍由现有 `store/graph.py` 中的读模型定义。缓存构建器与 SQL 路径必须调用同一批派生函数，避免两套口径。缓存层只负责存储、失效与提供邻接读取，不重新解释置信、审核状态或关系类型。

## 4. 缓存内容

缓存保存不可变邻接记录与最少量的节点描述，按节点 ID 建正向和反向两组索引。每条记录保留关系类型、方向、置信、权重、`source_table`、`source_id`、证据引用、版本、profile 与租户，足以复用现有边对象构造和结果裁剪逻辑。

节点最终仍由事实表派生函数组装；缓存中的节点描述只用于 traversal 过程中识别邻居与标签，不承载新的业务字段。关系类型掩码、置信过滤、`relation_types`、`include_ambiguous` 都在查询时应用，不固化进缓存条目。

序列模式的相邻对展开也进入同一邻接结构，但必须在缓存键中携带 `graph_pattern_limit`；模式候选集合变化时不能使用旧快照。

## 5. 缓存键与失效

缓存键包含后端类型、数据库文件绝对路径或连接串的稳定摘要、租户、版本、profile 身份、`include_ambiguous`、`graph_pattern_limit` 与事实水位。深度、节点数、扇出和查询预算不进键，因为它们是查询时参数，不改变邻接事实。

事实水位必须覆盖所有参与图派生的事实：调用实例、审核状态、API 实体及其基类、导入边、文档强边、文档链接、特征节点与链接、簇成员、序列模式、模式覆盖与一致性判定。SQLite 用 `PRAGMA data_version` 加进程内写入计数共同判断；PostgreSQL 可用保守的 WAL 位置变化判断，无法可靠取得水位时禁用缓存。

缓存按水位差异自然失效：发现新水位后构建新快照并原子替换，旧快照等待空闲驱逐。构建失败不得留下部分条目。进程内采用引用计数加空闲时间驱逐，不启动后台定时线程。

## 6. 构建与内存边界

首次需要邻接时惰性构建，按贡献表顺序扫描，不逐节点查询。构建过程复用现有派生函数，但把行到边的转换集中执行，避免重复解析同一模式或同一 API 名称。

新增 `graph_cache_enabled`、`graph_cache_max_edges`、`graph_cache_ttl_seconds` 三个配置。缓存边数超过上限、内存分配失败或后端不支持水位时直接回退 SQL 路径，不截断查询结果。实现配置时需同步配置默认值、示例配置与用户文档。

## 7. 查询执行与预算

在 `store/graph.py` 内引入一个邻接提供接口：现有 `neighbors()` 通过该接口取边。SQL 路径仍走当前事实表查询；缓存路径从快照取边。预算计数从“SQL 语句次数”调整为“逻辑邻接读取次数”：缓存命中也计一次，确保缓存不会绕过 `graph_query_budget` 的硬边界。

这一调整保持配置名不变，但需要在落地时同步更新配置说明与审核文档。深度、节点数、扇出、关系过滤、截断标记和证据输出保持当前语义，缓存路径不得引入新的排序或隐藏的过滤。

## 8. 回退与可观测

缓存不可用时不改变调用结果，只改用 SQL 路径。构建次数、命中率、回退原因、快照边数和构建耗时记入内部指标或调试日志；首轮不扩展 Web/MCP 返回结构。若后续要把缓存状态暴露给调用方，必须同步 OpenAPI 快照、前端类型和工具文档。

## 9. 测试与验收

- 同一组 gold 用例分别走 SQL 路径与缓存路径，节点集合、边集合、证据引用、权重与截断标记一致。
- 插入或审核一条调用后，下一查询使用新快照，不返回旧边。
- 预算在缓存命中时仍然生效并正确设置截断。
- 缓存容量或水位不可用时回退 SQL，结果不缺失、不静默截断。
- 同一键的并发查询只构建一次快照。
- 在可用环境中补 Postgres 差分测试；不可用时按既有后端测试惯例跳过。

## 10. 实施顺序

先抽出共享的边派生函数并做无行为变化差分测试；再引入邻接提供接口与每次查询内的临时记忆化；随后实现进程内快照并默认关闭；最后用真实语料基准确认收益后再启用。派生邻接缓存始终是可重建优化，不改变 SQLite 与事实表作为唯一真相的地位。
