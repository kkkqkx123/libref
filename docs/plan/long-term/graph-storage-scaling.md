# 图查询存储规模与选型阈值

> 位置：`docs/plan/long-term/` 长效设计。记录当前代码仓与基准语料的实际规模、单版本图事实分布、实测图查询延迟，以及“两项优化足够”与“需要图数据库”的规模边界。数据来自本地快照，不含生产环境推测。

## 1. 统计口径

图查询强制绑定单一版本、单一 profile、单一租户，因此选型依据是**单版本活跃图**，不是整库文件大小，也不是代码仓库总行数。

记：

- `N`：单版本活跃图节点数，主要来自 API 实体、文档块、文件、模式、簇与特征节点。
- `E`：单版本活跃图边数，主要来自调用、导入、强文档边、模式相邻边、成员边与父链。
- `F`：参与图派生的事实表行数，含调用实例、审核状态、文档强边、模式、簇、特征链接等。
- `Q`：图查询并发与尾延迟目标。

## 6. 实测图查询延迟

测试对象为 gradle `v9.9.1` 中调用次数最高的实体：

`org.gradle.api.internal.project.MutableStateAccessAwareProject.onMutableStateAccess`

默认配置：`graph_max_depth=2`、`graph_max_nodes=200`、`graph_max_fanout=20`、`graph_pattern_limit=200`、`graph_query_budget=400`。

放宽配置：节点上限 2,000、扇出上限 200、预算 20,000，其余同默认。

| 模式 | 方向 | 深度 | 配置 | 结果 | 耗时 |
|---|---|---:|---|---|---:|
| neighbors | forward | 1 | 默认 | 1 节点 / 0 边 | 约 2 ms |
| neighbors | backward | 1 | 默认 | 21 节点 / 20 边，扇出截断 | 约 4 ms |
| neighbors | both | 2 | 默认 | 22 节点 / 41 边 | 约 7 ms |
| neighbors | backward | 2 | 放宽 | 66 节点 / 65 边 | 约 13 ms |
| neighbors | both | 2 | 放宽 | 66 节点 / 129 边 | 约 16 ms |

当前规模下图查询处于毫秒级；延迟主要受返回规模影响，尚未触及事实表扫描瓶颈。

## 7. 选型分析

### 7.1 当前档位

当前最大单版本活跃图约：

- `N`：1～2 万 API 与文档节点量级；
- `E`：数万条调用、导入与强边量级；
- `F`：单版本事实表行数不超过约 2 万～3 万，文档侧原始对齐最多约 11 万但强边仅数百到数千。

这属于小到中等规模。现有索引、关系过滤、查询预算、节点与扇出上限已经足够，不需要图数据库，也不需要立即启用长期优化。

### 7.2 两项优化的覆盖范围

已设计的两项优化是派生邻接缓存与序列模式邻接展开去重。适用于：

| 条件 | 边界 |
|---|---|
| 单版本节点 `N` | 5 万～50 万 |
| 单版本边 `E` | 10 万～100 万 |
| 参与事实 `F` | 100 万～200 万 |
| 查询形态 | 深度不超过 5、节点上限 200、扇出上限 20～200 的有界邻域与路径 |
| 访问分布 | 热点版本集中，进程内缓存可形成命中 |
| 尾延迟目标 | 两项优化后 `p95` 不超过 100～200 ms |

按当前最大源码版本外推：

- 放大 5 倍：约 7 万 API、10 万调用、4.5 万导入，处于当前档与扩展档交界；
- 放大 20 倍：约 28 万 API、38 万调用、18 万导入，仍在两项优化可覆盖区间。

因此，两项优化足以支撑当前最大单版本规模约 5～20 倍的增长。

### 7.3 图数据库边界

满足以下任一条件时，应启动图数据库或专用图服务评估：

1. 单版本活跃边长期超过 100 万～500 万，且两项优化后 `p95` 仍不能达标。
2. 单版本活跃节点进入百万级，或冷版本随机访问导致缓存命中率长期偏低。
3. 查询形态从有界邻域变为连通分量、全图统计、子图匹配、跨版本遍历、深度全局路径或图导出。
4. 写入频繁导致事实水位不断变化，邻接快照反复失效，内存预算被热点版本撑满。
5. 并发达到数百 QPS，且多进程都需要访问大图。
6. 多个外部系统需要统一图查询 API、分页、图算法与独立容量治理。

参考调研中 850 万节点、1,690 万边的 SQLite 递归遍历约 6.6 秒；django 规模图约 20～100 ms。这说明百万到千万级活跃图才是图数据库或专用邻接服务的明确分界。

## 8. 结论

- 当前基准库整体约 717 MB，但单版本图只有数万节点、数万边；实测毫秒级，不需要图数据库。
- 两项长期优化是下一档能力，适合支撑当前最大单版本规模约 5～20 倍的增长。
- 只有当活跃图进入百万节点 / 数百万边，或查询升级为全局图分析时，才应引入图数据库。
- 图数据库若引入，也必须定位为可重建派生索引；SQLite 事实表仍是唯一真相。
- 后续复核应重新统计单版本 `N/E/F` 与 `p50/p95/p99`，用实测数据校准上述阈值，而不是只按整库大小或代码行数决策。
