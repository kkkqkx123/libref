# 序列模式邻接展开去重设计

> 位置：`docs/plan/long-term/` 长效设计。针对 `seq_patterns` 展开时的重复扫描和逐对实体反查问题；目标是减少查询内的重复工作，同时保持 `pattern_next` 边的证据与权重语义不变。

## 1. 背景与目标

当前 API 节点每次展开都会读取 `graph_pattern_limit` 条高分模式，对模式中的每一对相邻 API 再按名称反查实体。两跳邻域会对多个节点重复执行同一批查询；不同模式也常常包含相同的相邻对，生成多条语义重复的边。

目标是把模式展开改为一次构建、多次查找的读模型：同一查询内只扫描一次候选模式，只解析一次实体名称，并把相同相邻对合并成一条确定性边。

## 2. 范围与非目标

范围是 `store/graph.py` 内 `pattern_next` 边的派生过程，以及它与查询预算、邻接缓存的关系。非目标是修改 PrefixSpan 挖掘算法、改变模式支持度定义、新增模式事实表，或把模式边升级为调用边。

## 3. 现有问题

模式扫描按节点触发，候选集合固定为支持度最高的一批模式，但每个节点都会重读并重解析。名称反查按相邻对逐个发出，形成读放大。相同相邻对出现在多个模式中时会生成多条边，边的排序依赖哈希化的边 ID，证据出处不稳定；支持度也没有明确的合并口径。

## 4. 查询内索引

每次图查询首次需要 `pattern_next` 时，构建一次查询内索引。读取阶段仍按支持度降序、模式 ID 升序取 `graph_pattern_limit` 条模式；解析阶段一次性取出这些模式涉及的 API 名称，按版本与租户建立名称到实体节点的映射，并要求限定名唯一。

索引按方向组织，以源实体名称为键，值为目标名称、模式 ID、支持度、位置与完整模式组成的候选列表。节点展开时只按自身标签查表，不再读取事实表。该索引仅存在于本次 `GraphView` 生命周期内，不写入数据库。

## 5. 合并与权重口径

合并键取实体节点 ID 对与关系类型 `pattern_next`，与 BFS 候选去重口径一致。多个候选指向同一对实体时，选取支持度最高的模式作为代表；支持度相同则按模式 ID、位置升序取第一个，保证确定性。

边的 `weight` 使用代表模式的支持度，不跨模式累加。证据保留完整模式、支持度、位置与来源模式行 ID；这样既表达结构强度，又不把重叠模式的支持度重复计入。重复候选只影响代表选择，不产生多条边，也不改变现有节点裁剪逻辑。

## 6. 与预算和缓存的关系

索引构建阶段按现有查询预算规则计费；后续节点展开只计一次逻辑邻接读取。若实现邻接提供接口，模式展开应与普通邻接共用预算计数，避免缓存命中后绕过边界。

进程内邻接缓存落地后，模式索引成为快照构建的一部分，缓存键继续包含 `graph_pattern_limit`。查询 `pattern_next` 时从快照直接取合并后的边，不再单独构建索引；快照失效时随整个邻接快照一起重建。

## 7. 测试与验收

- 构造包含重复相邻对的模式，断言只返回一条 `pattern_next` 边，代表模式与权重符合确定性口径。
- 同一 gold 用例在重构前后比较节点、边、证据引用和截断标记，确认行为不变。
- 数量化验证：同一查询内模式表扫描与实体名称反查只发生一次，展开更多节点不再增加事实表 SQL。
- 覆盖 profile、租户与版本隔离，确保索引不跨作用域复用。
- `graph_pattern_limit=0` 时完全关闭模式展开，不产生额外读取。
- 与邻接缓存组合后运行差分与失效测试，确认模式变化能触发新快照。

## 8. 实施顺序

先在 `store/graph.py` 内加入查询内索引与合并逻辑，保持 SQL 路径不变并做差分测试；再把它接入邻接提供接口统一预算计数；最后随邻接缓存一起进入快照构建。该优化只降低读取次数，不引入新的语义或排序权重。
