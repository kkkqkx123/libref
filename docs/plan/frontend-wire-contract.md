# HTTP 契约的四项收口设计

> 范围：`docs/plan/frontend-schema-typing.md` 中刻意保留的四项开放点——任务种类、
> 动态错误码、历史时间表示、逗号串多值参数。本文给出是否需要正式实现的判断和独立实施方案；
> 主方案文只记录结论链接，具体改动以本文为准。

## 总体判断

四项都需要正式实现，但理由不同：任务种类是“开放输入导致任务无法执行”，错误码是“稳定标识
靠文本推断”，时间表示是“同一语义多种线缆格式”，多值参数是“前端数组与后端字符串两套模型”。
它们都不是纯类型美化，而是会改变请求是否能执行、错误能否本地化、时间能否正确解析的契约问题。

实施顺序建议：多值参数 → 时间表示 → 错误码 → 任务种类。前两项改动面窄、验证直接；错误码需要
逐站点替换；任务种类涉及工作进程注册与前端表单，放最后可以复用前三项的错误码和时间契约。

## 一、任务种类

### 现状与问题

服务层已有四种任务：`scrape_docs`、`index_repo`、`mine_patterns`、`induce_labels`。前两种由
入库申请创建，后两种在 CLI 异步命令中创建。`POST /jobs` 只拒绝前两种，接受任意字符串；
组合服务的 worker 却只注册了文档抓取和仓库索引两个 runner，因此通过任务中心“新建任务”
提交的任意种类都会异步失败。前端当前用自由文本框填写种类与 JSON 参数，无法表达这种约束。

### 决策

正式实现“种类闭合 + 执行闭合”，而不是只把字符串改成字面量联合。指的是：
`POST /jobs` 只允许两种可直接提交的种类，组合 worker 必须注册对应 runner；两种索引种类
继续只能由入库申请产生。任务详情的 `kind` 使用同一个闭合联合，失败历史数据不再兼容。

### 设计

后端在任务模块集中定义种类常量与联合类型，路由模型与 worker 分派共用同一份定义。
`JobCreate` 按种类做判别联合，参数分别为挖掘参数与标签归纳参数；`JobDetail` 的
`params` 与 `result` 按种类收窄，真正自由形态的结果才保留 `JsonValue`。
组合服务的 lifespan 注册两个新 runner，取消接口继续显式拒绝入库申请 backed 任务。

前端任务中心的“新建任务”改为两种固定选项，参数输入从自由 JSON 文本框改为按种类生成的
表单；对无法在任务中心处理的索引任务，只提供“打开对应入库申请”的引导，不再提供重提按钮。
任务详情按 `kind` 窄化后展示参数与结果。

### 影响面与验收

- 后端：`services/infra/jobs.py`、`services/code/mining_refresh.py`、`web/api.py`、
  `web/app.py`、`cli/ops_commands.py`。
- 前端：`views/JobsView.vue`、`api/types.ts`。
- 测试：原先用 `noop` 制造失败任务的用例改用受支持种类加非法参数；新增两种 runner 的分派用例；
  契约测试断言 `kind` 枚举与按种类参数 schema。
- 验收：任务中心新建的两种任务都能进入终态；任意种类提交在请求阶段即被拒绝，
  不再产生永远不会执行的排队任务。

## 二、动态错误码

### 现状与问题

错误响应带 `error` 字段，但约五十处路由仍直接抛 `HTTPException` 并传原始文本，
`errors.py` 再按状态与文本前缀猜测代码；前端把代码表声明为 `Record<string, string>`，
未登记的新分支只显示原文。`http_<状态码>` 兜底本身是合理的，但目前它与“真实稳定码”
混在同一个字符串类型里，调用方无法区分“已知错误”和“未归类错误”。

### 决策

正式实现显式错误码：任何拒绝点都必须声明代码，删除从 `detail` 文本推断代码的逻辑。
已知代码形成闭合联合；未归类错误使用 `http_<状态码>` 模板字面量类型，前端展示原文但不
尝试翻译。代码表只保留界面真正需要分支的粒度，不按每条 `ValueError` 文案扩张。

### 设计

后端在 `web/errors.py` 定义唯一的代码清单与 `ApiRejection` 类型，清单包含现有中英文词条
覆盖的稳定码，并补入配置刷新失败、入库申请冲突等当前落入通用码的分支。任务种类由请求模型
在解析阶段拒绝，不另设错误码。
所有路由与中间件拒绝点改用 `ApiRejection` 并显式给定代码；服务层异常继续保留原始
`detail` 文本，由各路由决定映射成哪个代码。`_EXACT` 与 `_PREFIXES` 文本匹配整体删除，
`error_body` 不再推断代码。

`ErrorResponse.error` 与配额详情中的 `error` 使用生成的代码联合；前端 `ApiError.code`
使用同一联合加 `http_<状态码>` 兜底。`i18n` 的错误码映射改为对已知代码穷尽，
新增代码若未同时补齐两份词条，门禁即失败。

### 影响面与验收

- 后端：`web/errors.py`、`web/app.py`、`web/middleware.py`、错误契约与鉴权集成测试。
- 前端：`api/client.ts`、`api/types.ts`、两份语言词条、i18n 检查脚本。
- 测试：契约测试断言 `ErrorResponse.error` 为枚举；逐类拒绝测试断言代码而非文案片段；
  词条门禁断言代码集合与词条键集合一致。
- 验收：新增一个错误分支时只改拒绝点与两份词条，不再修改文本匹配表；界面能区分
  “已本地化错误”和“未归类错误 + 原始详情”。

## 三、历史时间表示

### 现状与问题

存储层用 epoch 秒保存密钥有效期，用 SQLite 朴素 UTC 文本保存多数创建时间，配额模块又生成
ISO 字符串；HTTP 边界同时暴露 epoch 数字、朴素文本和 ISO 文本。`KeyCreate.expires_at`
要求数字而 `ApiKeyRow.expires_at` 返回字符串，`ErrorResponse.reset_at` 甚至声明为
`number | string`。前端格式化器为了兼容三种输入保留了数字推测与正则解析，无法从类型上
保证时间语义。

### 决策

正式实现“存储不变、HTTP 边界唯一格式”：所有响应时间与错误重置时间统一为带时区的
ISO 8601 字符串；有效期输入也改为 ISO 字符串，由路由在调用服务前转换为 epoch。
不为旧的数字或朴素文本保留兼容分支。

### 设计

后端在 web 层集中一个时间归一化出口，将 epoch、SQLite 朴素 UTC 文本与已有 ISO 文本统一
序列化为 `Z` 结尾字符串。响应模型中的时间字段统一使用带 `date-time` 格式的字符串模型，
覆盖密钥、任务、审核、反馈、版本与配额等字段；`KeyCreate.expires_at` 改为 ISO 字符串输入，
转换发生在路由层，`services/infra/auth.py` 继续以 epoch 与存储层交互。
`ErrorResponse.reset_at` 与 `QuotaErrorDetail.reset_at` 收窄为字符串或可空字符串，
配额模块生成的字符串直接透传。

前端从生成类型派生品牌化的 ISO 时间类型，替换各视图时间字段的裸 `string`；
`parseTimestamp` 只接受 ISO 字符串与空值，删除数字推测和朴素 UTC 正则。
所有时间展示统一走 `useFormatters`。

### 影响面与验收

- 后端：`web/api.py`、`web/app.py`、`web/errors.py`、`web/middleware.py`、
  `services/ops/index_requests.py`、相关服务返回的朴素时间字段。
- 前端：`api/types.ts`、`i18n/format.ts`、任务/审核/反馈/管理视图。
- 测试：契约测试断言时间字段格式；集成测试断言密钥有效期往返、配额重置时间和列表时间
  均为带时区字符串；原先断言数字 `reset_at` 的用例改为 ISO 字符串。
- 验收：前端不再需要猜测单位为秒还是毫秒，也不再依赖“无时区即 UTC”的隐含约定；
  同一时刻在列表、详情与错误提示中渲染一致。

## 四、逗号串多值参数

### 现状与问题

五个洞察接口的 `apis`、`pattern`、`containing`、`resolve_kinds` 在契约里是字符串，
服务层再按逗号拆分；前端状态是数组，调用前在五个视图里手动 `join(',')`，深链状态也用
逗号编码。逗号串与地址栏编码耦合，值本身含逗号时无法表达，且生成类型无法提示
“这里应传数组”。

### 决策

正式实现为真正的重复查询参数。后端声明数组，前端统一序列化，深链也改为重复键；
不保留逗号串解析，也不同时接受两种写法。

### 设计

后端查询模型将上述字段改为 `list[str] | None`，删除路由中的 `str` 参数与拆分调用，
服务层仍接收列表，MCP 与 CLI 调用不受影响。OpenAPI 因此生成数组类型，前端
`api()` 的查询序列化统一把数组展开为重复键，不再在视图里拼接。

`utils/query.ts` 的快照与读取函数改为数组语义：写入时保留数组，读取时只接受数组；
深链形式从 `?pattern=a,b` 变为 `?pattern=a&pattern=b`。五个洞察页直接把数组传给
查询参数，不再各自调用 `join(',')`。相关接口映射文档与规划文档同步更新示例。

### 影响面与验收

- 后端：`web/api.py`、`web/app.py`。
- 前端：`api/client.ts`、`utils/query.ts`、五个洞察视图及其查询同步测试。
- 测试：契约测试断言四个字段为数组；集成测试用重复键提交多值并断言结果；
  前端测试断言地址栏往返后数组内容不变。
- 验收：复制地址栏链接能复现同一多值筛选；含逗号的值不再被截断；
  后端不再持有“字符串转列表”的重复逻辑。

## 共通约束

- 四项都改变 HTTP 契约，按项目约定不做旧格式兼容，快照与生成物在同一次改动中一起更新。
- 错误码与时间字段是全站横切改动，契约测试与前端 `npm run check` 必须同时通过。
- 任务种类与时间归一化会触及服务层，除契约测试外还需为新增的 runner 与时间转换补单元用例。
- 每项单独提交并在提交后跑一次完整后端与前端校验，不把四项合并成一次大改动。

## 落地结果

四项已按顺序实现。多值查询参数改为重复键，前端请求与深链统一由数组序列化；响应时间与
配额重置时间在服务读模型和错误体中统一为带时区的 ISO 字符串，密钥有效期改为 ISO 输入；
所有拒绝点改为显式稳定码，错误码枚举进入生成类型并约束两份词条；任务种类在请求模型中
闭合，组合 worker 注册挖掘与标签归纳 runner，任务中心改为固定种类表单。

与方案的偏差：任务种类的非法值由 FastAPI 在请求解析阶段以 422 拒绝，而不是走
`ErrorResponse` 的专用错误码；这样种类约束只在一处定义，无需再维护一份运行时码表。

验证：`pytest`、`ruff`、`ruff format --check`、`mypy src`、`npm run check` 与
`npm run build` 均通过。
