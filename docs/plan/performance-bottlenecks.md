# 性能瓶颈清单与改进分析

本文基于首轮性能基准、真实仓库挖掘记录与当前代码路径，列出已确认和待确认的性能瓶颈，并给出改动方向。只分析实现方案，不在本文改代码；结论优先使用同机相对数据，绝对耗时只用于说明量级。

## 一、结论摘要

当前最值得先动的不是检索单查询延迟，而是索引与挖掘链路：

1. **挖掘重算重复读取调用集**。一次挖掘对 `call_instances` 的主过滤读取出现四次；在 1558 条目标调用上完整挖掘约 0.9s，规模扩大后会按读取次数成倍放大。
2. **文档净化的成本被证实最高，但缺少子阶段归因**。三个冻结夹具重建中位数约 4.1s，其中净化阶段约 1.3s，而分块与落库合计不足 0.2s；需要先分清 HTML 解析、剪枝、Markdown 转换与缓存键开销。
3. **用法摄取保留了代码检索专用分支**。非实现来源仍写源码分段并触发向量同步，目标声明按全版本实体加载，这两处随语料规模增长的风险高于当前小夹具所显示的成本。
4. **标签归纳和读视图存在按 API 或按视图重复的查询**。兄弟 API 查询逐个发出，档案上下文在一组读路径中重复解析，健康视图读取上限为十万行；这些是中大规模语料下的结构性风险。
5. **AST 冷启动是真实但一次性的开销**。热解析稳定在 2–3ms，冷解析按语言在约 8–147ms；只应在长驻 Worker 中按需预热，不适合为一次性命令行全局预热。
6. **检索与 Web 暂不构成主要瓶颈**。FTS 约 1ms，三档检索约 4–6ms，进程内 Web 每批 8 个请求约 46ms；查询计划已走索引，没有证据支持先改这些路径。

## 四、逐项分析

### 1. 一次挖掘重复扫描调用集

`mine_patterns` 先调用 `_load_kept_calls` 构造序列，随后 `refresh_feature_tree`、`refresh_clusters`、`refresh_facets` 分别以同一组过滤条件再次调用它。空结果时 `_empty()` 也会进入同样的刷新分支。审计显示 1558 条目标调用被主过滤读取四次。

改进方式是把“调用集加载”上移到一次编排：由 `mine_patterns` 解析档案、过滤与评审状态后得到一份内存行集，再把它作为必需输入传给三个刷新函数。刷新函数不再自己查 `call_instances`，只负责从行集投影出自己需要的字段并写派生表。空结果时清理一次派生表后直接返回，不再触发刷新。

需要注意三点：

- 现有 `_load_kept_calls` 承载档案来源、评审状态、目标状态、宏策略等口径，不能在各刷新函数里重写过滤；只搬调用位置。
- 新接口直接替换旧参数，不保留“传了行集就用、没传就再查”的双路径，否则重复扫描会悄悄回来。
- 计数门禁在优化落地后立即从“观察”改为硬断言：一次 `mine_patterns` 的主过滤读取必须是一次。

预期效果是把调用集读取从四次降到一次。当前小夹具上可节省约 0.6s；真实数万调用语料上收益更大，且减少 SQLite 页缓存抖动。

### 2. 无界挖掘参数

`mine_patterns` 与 CLI 默认值有界，但参数本身没有合法性约束，任务参数也可直接传入 `minsup=1`、`minlen=1`。历史记录显示这种组合在数万目标调用上会产生大量模式并超过 40 分钟未完成。

改进方式是在服务入口统一校验下界与上界：支持度至少为 2，序列长度至少为 2 且不超过配置上限，并要求结果上限或会话级容量预算。CLI 与任务参数共用同一校验，不在出口层另写一套规则。容量实验如需无界组合，走显式周期性任务，不调用常规服务入口。

基准侧已有有界 PrefixSpan 规模阶梯和无界容量档的划分；把参数校验纳入后，`capacity` 档继续记录爆炸曲线，但不进入常规门禁。

### 3. 文档净化与正文抽取

净化阶段包括缓存键哈希、HTML 解析、链接绝对化、噪声节点剪枝、正文选择、Markdown 转换和归一化。当前只测到整段耗时，无法判断是解析、剪枝还是转换主导。直接优化最大函数风险较高。

先在基准里补一个纯函数微基准，分别测量：构造解析器、元数据与链接收集、噪声标签删除、评分剪枝、根节点序列化、Markdown 转换、归一化与 SHA1 键计算。输入取现有冻结文档正文，不新增网络夹具。拿到归因后再决定：

- 若 Markdown 转换占主导，评估是否需要全量 `inner.html` 序列化，以及是否可只对保留子树转换；
- 若评分剪枝占主导，合并重复 CSS 查询与节点遍历，复用已收集的节点度量；
- 若链接收集占主导，把结构链接与正文链接合并为一次遍历；
- 若 SHA1 缓存键占主导，缩短参与哈希的指纹输入，但不能把正文排除到键外导致错命中。

这一项先做归因，不直接改算法。文档质量门禁对正文和链接顺序敏感，任何改动都要跑检索质量基准的文档夹具。

### 4. 非实现来源的分段与向量写入

`code_ingest` 的 `_index_repo_inner` 对所有来源统一执行 `_store_source_chunks`，并在向量与嵌入可用时逐批 `_sync_docs`。但官方示例、参考项目等来源的用途是挖掘调用事实，不参与代码检索时这些分段与向量准备是非必要分支。

改进方式是把摄取目的显式化：实现来源继续写实体、导入边、源码分段与向量；纯用法来源只保留来源事实、解析缓存、实体/调用身份和调用行。调用方通过明确参数选择摄取目的，不在读取端猜测角色。删除该分支后，小夹具上的收益可能有限，但大批量参考项目摄取会直接少一整条写路径。

验收要同时看计数和时间：调用数、样本数、来源行不变；源码分段与向量写入次数归零；构建耗时下降。质量测试需覆盖“该来源不参与代码检索”的语义，避免把有用的代码检索语料误关掉。

### 5. 目标声明与目标名全量加载

非实现来源解析时，`target_declarations` 读取版本的全部 `api_entities` 并构造成内存记录；紧接着又以全量 `qualified_name` 读入集合，再按 `target_filter` 的前缀在内存过滤。实体数增长时，这两处会重复搬运不需要的行。

改进方式是把显式名称与前缀条件下推到 SQL，只加载本次来源实际可能调用的目标声明与目标名集合；一次索引运行内复用同一份结果，不再按来源重复构造。没有前缀时仍需全量加载，但此时全量本身就是需求。

这项与问题 4 独立：即使保留分段写入，也应先消除与目标无关的全量实体加载。

### 6. 标签归纳的兄弟 API 查询

`induce_labels` 已批量预取参数形态，但每个 pattern API 仍单独调用 `related_apis`。`related_apis` 每次都重新解析版本范围、构造作用域 CTE、扫描调用并排序取前四；聚类标签路径也有同类调用。查询次数随 API 数与模式数线性增长。

改进方式是增加一个批量兄弟 API 查询：一次取回当前标签任务涉及的全部 API 及其同作用域邻居，在内存中按目标 API 分组，再复用现有截断与去重规则。保留单 API 接口给交互查询，但批量归纳路径不再调用它。

验收用 SQL 计数：兄弟查询次数应与 API 数解耦；输出标签的 `siblings` 排序与截断规则保持一致，需有差分测试比对批量前后的标签输入。

### 7. 档案上下文重复构造

`_profile_context` 会查询 `mining_profiles`，再对每个档案解析来源 JSON 并调用 `profile_source_context` 读取 `code_sources`、`target_filter`、提交标识等。一次健康或洞察请求中，多个列表方法分别调用它，导致同一档案身份被重复解析和拼接。

改进方式是在一次读请求边界解析一次档案上下文，并把它作为参数传给需要它的列表方法。实现时保持读服务为无状态：上下文是请求内对象，不缓存到进程全局，避免配置与来源更新后读到陈旧指纹。若保留公开方法签名，可让每个公开入口自行构造上下文，内部私有方法只消费已构造结果。

这项改动应与问题 8 一起做，因为健康视图是重复调用最密集的入口。

### 8. 健康视图无界读取

`mining_health` 以 `limit=100000` 读取全部模式与聚类，再把整批行交给 `reuse_diversity`。指标本身只是计数与对数运算，成本主要在取行和 JSON 解析。全量语料下这会把健康视图变成一次派生表全表扫描。

改进方式是给健康视图定义明确的统计口径：默认用有界随机或分层样本，输出中记录样本数、总体数与是否截断；需要全量的运维场景显式选择。实现可在读服务内用 SQL 计数加有限取样，避免把十万行全部构造成字典。

注意健康指标会随样本口径变化，必须先固定差分测试的期望关系，再替换默认行为；不能直接把旧数值写成新门禁。

### 9. 证据作用域表达式

`_scope_of` 在分组、连接和过滤中仍用 `COALESCE(scope, caller_file || char(0) || caller)`。迁移已经回填 `scope`，写入路径也持久化该列，索引 `idx_call_instances_scope_key` 已存在。表达式让 SQLite 难以直接使用该索引。

改进方式是让读模型统一使用持久化的 `scope` 列，删除拼接回退路径。项目不做历史数据兼容，因此不需要保留空值回退；只需确认所有写入入口都填了 `scope`，并用迁移测试保证新库字段非空。

验收用查询计划审计：证据、共现和健康计数中的作用域条件应出现索引查找而非表达式扫描。当前基准只审计了 FTS 作用域计划，下一步把同类审计扩到调用证据。

### 10. AST 冷启动

`extract_file` 首次按语言创建解析器并编译四类查询，之后复用进程内缓存。实测冷解析从 Go 的约 8ms 到 C# 的约 147ms，热解析稳定在 2–3ms。对单文件 CLI 调用，冷启动可能占总耗时大头；对长驻索引服务，只影响进程启动后的首轮。

改进方式不是全局预热所有语言，而是在长驻 Worker 接到任务后，按该任务实际出现的语言集合预热解析器和查询；一次性命令保持懒加载。这样避免为只处理 Python 的任务支付十种语言的编译成本。

缓存是进程内的，不要为了跨进程复用而序列化 tree-sitter 查询；复杂度收益不抵维护成本。

### 11. 真实模型与向量后端覆盖缺口

当前检索基准用哈希词袋嵌入与词覆盖重排，三种预设的 median 分别为约 4.3ms、4.5ms、6.1ms。这个口径适合验证排序逻辑，不包含真实编码、网络往返、重排端点与向量后端的成本。历史归档记录显示全量真实编码约七万块，耗时由端点速率决定。

改进方式是增加一个显式 `service.retrieval_real` 容量用例：固定同一批查询，分别记录查询编码、向量检索、重排请求和装配耗时，密钥只从环境读取，结果不进入默认门禁。Qdrant 与 simvec 分别给基线，不混在一行。

在这项数据出来前，不优化真实模型重试、端点共享状态或向量批量参数；离线替身无法证明这些改动有效。

### 12. Web 并发

进程内 Web 用例的每批 8 个请求约 46ms，接近服务层单查询 4ms 加框架与鉴权开销的预期；并发 1 与 4 没有稳定差异。ASGITransport 和应用线程模型会限制并发解释，不能据此判断生产容量。

改进方式是先补真实 ASGI 服务器下的外部并发基准，记录每秒请求数、p50/p95/p99 与错误率，再决定是否优化。代码层面值得核对的两点是每请求服务装配和 SQLite 会话创建，但临时测得每请求重放迁移只比裸开连接多约 0.06ms，不构成优先项。

## 五、明确不先动的地方

- FTS 作用域查询约 1ms，查询计划已使用覆盖索引；不要重写全文检索。
- 有界 PrefixSpan 的耗时随规模近似线性增长，分块耗时也随副本数线性增长；当前没有超线性证据。
- Web 出口在进程内测试中未显示独立瓶颈；缺少真实服务器数据前不调整鉴权或服务装配。
- 原生 simvec 已有 Criterion 基准；Python 侧不重复测距离核与建图。
- 不为了优化而恢复历史空值回退或旧接口；所有替换直接删掉旧路径。

## 六、实施顺序与验收

按“先计数、后计时；先结构、后微优化”的顺序推进：

1. 合并调用扫描，并把审计计数改成硬门禁；同步加入无界参数校验。
2. 补 HTML 抽取子阶段基准，完成归因后再改生产模块。
3. 拆分用法摄取目的，下推目标前缀过滤，验证调用事实不丢失。
4. 批量化兄弟 API 查询，复用读请求内档案上下文，收敛健康视图读取范围。
5. 把作用域表达式替换为持久列，并扩展查询计划审计。
6. 长驻 Worker 按任务语言预热解析器；一次性命令不变。
7. 增加真实模型、向量后端与真实 Web 服务器容量用例，再对这些路径做优化。

统一验收口径：

- 结构计数必须精确：调用集扫描次数、兄弟 API 查询次数、分段写入次数、档案解析次数。
- 计时只与同机基线比较；噪声带内的变化记为平手，不写成收益。
- 涉及派生输出的变化先做差分测试，再改默认行为。
- 每项改动完成后，更新 `docs/archive/perf/` 的新一轮记录，而不是覆盖旧结论。
