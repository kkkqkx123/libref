# API 使用特征挖掘集成修复计划

本文记录 `docs/analysis/api-usage-mining-redesign.md` 落地后的代码审查结论与修复顺序。目标是补齐“定义来源与用法来源分离、证据可追溯、档案可复现”三条主链路，不引入旧口径回退。

## 阶段一：索引申请参数透传

- MCP/Web 的仓库索引申请已经暴露 `source_role` 与 `target_filter`，但 `IndexRequestService._resolve_payload` 生成的可重放参数没有携带它们，审批后退回默认实现角色。
- 将两个字段纳入归一化参数与去重键；CLI 的索引申请命令同步暴露相同参数。
- 验收：三个出口提交的同一角色与过滤条件生成相同申请；不同角色生成不同申请；审批后 job 参数保留角色与过滤。

## 阶段二：文档代码块语料归属

- 页面级 `sample_prefix` 已含 URL，但 `ingest_snippets` 按版本复用同一个 `source_key`，导致每次页面摄取都会清扫掉其他页面的调用。
- 改为按页面注册语料源，把 URL、标题与选择规则写入语料源记录；保留 URL 与围栏序号作为样本身份。
- 验收：连续抓取两个页面的代码块后，两个页面的调用都保留；每个来源的 `source_url` 与证据一致。

## 阶段三：定义来源与用法来源彻底分离

- 移除“没有实体就由 usage 仓库自行补定义”的分支；usage 索引在没有目标实体且没有显式过滤时不得把局部声明写成目标 API 事实。
- 非实现角色在没有目标名集合也没有前缀规则时，调用默认不命中目标 API，避免无过滤文档片段全量进入挖掘。
- 验收：先索引参考项目再索引目标库时，`api_entities` 不包含参考项目声明；无目标约束的文档片段 `in_target_api=0`。

## 阶段四：档案身份与覆盖参数

- `source_roles`/`source_ids` 覆盖不得改写默认 `usage` 档案。默认名加覆盖时生成带指纹的独立档案；具名档案在显式给出来源集合时允许创建，否则仍要求预先存在。
- 档案指纹纳入语料源的身份、选择规则、commit 与目标过滤；仓库源注册在拿到 commit 后补写提交号。
- 验收：带角色覆盖的挖掘之后，默认 `usage` 档案的来源集合不变；改变选择规则或 commit 会改变档案指纹。

## 阶段五：样本身份与证据可读性

- `sample_id` 纳入语料源命名空间，避免不同来源的相同相对路径与函数名碰撞；片段调用继续用合成路径保持唯一。
- 读模型在证据与标签中展示来源角色、来源键、样本身份和档案指纹；问答的模式提示携带同样的档案信息。
- 验收：两个来源的同名文件不会合并为同一样本；证据输出可辨认官方示例、文档块、参考项目和内部实现。

## 阶段六：质量统计与存储边界

- `mining_health` 输出调用形态分布与宏覆盖率，明确宏展开未覆盖的限制。
- 标签表可用性检查改为后端中立写法，SQLite/PostgreSQL 行为一致。
- 验收：健康视图包含 `relations` 与 `macro_coverage`；两种存储后端都能读取标签。

## 阶段七：清理未接线代码

- 删除从未调用的 `matches_target`、`profile_id_for_version`、`library_source_names`、`entity_kind_suffixes`、`_persist_calls`。
- `dedupe_snippets` 接入文档/Rust 片段摄取，用于消除同批重复代码块。
- 验收：代码中不再保留上述空转入口；同一批内重复代码块只解析一次。

## 验证状态

- `python -m compileall -q src tests`、`ruff check src tests`、`ruff format --check src tests`、`mypy src` 均通过。
- `pytest -q` 通过：830 passed、35 skipped。
- 执行中修复了健康统计变量作用域、Markdown 页面标题变量作用域、Web 申请模型字段缺失与批量内重复代码块导致的旧测试口径问题。
- 新增离线人工核查渲染器与用例，输出到 `tests/e2e/outputs/usage_mining/`，覆盖来源、档案、模式差异、证据、健康与标签。
- 新增 DPDK v23.11 与 MTL v23.12 固定提交同步、真实索引与挖掘核查链路；`LIBREF_RUN_E2E=1` 用例通过，报告输出到 `tests/e2e/outputs/usage_mining_real/`。

## 暂不实施的范围

- 跨来源、跨页面的调用序列级去重：需要引入可配置的去重策略与保留多证据的读模型，单独作为后续任务。
- 参考项目版本兼容状态推断：需要依赖清单或目标版本约束输入，当前没有稳定事实来源，不以猜测标记版本不一致。
- probe 的代码块数量、目标 API 粗计数与 README 引用：现有 probe 明确只读且不解析文件，扩展会改变其职责边界，单独设计后再实施。
