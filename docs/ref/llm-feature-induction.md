# 用 LLM 直接归纳特征、代替训练模型的可行性分析

> 依据：`ref/EpiCoder` 实测代码 + `docs/ref/epicoder.md`、`docs/ref/codescholar.md`。
> 问题：EpiCoder 证明了"不训练任何模型、纯 LLM 归纳特征"的路线可以跑通；libref（以及 CodeScholar 的 GNN 路线）是否可以采纳？

## 1. EpiCoder 的实证：纯 LLM 路线确实成立

对仓库的核实结论：全仓库**没有任何 AST/静态分析工具**，特征完全由 LLM 产出，且端到端成功产出了 380k 级数据集。两个关键证据点：

1. **代码 → 语义特征**（`extract/extract_features.py::extract_single_feature`）：把源码填入 `prompt/extract/prompt12.txt`（21 类语义维度：workflow、数据变换、计算操作、错误处理、依赖库……），调 GPT-4，解析 `<begin>...<end>` 之间的 JSON。每文件一次调用，5 线程并发，jsonl 断点续跑。
2. **特征 → 分类树**（`extract/construct_tree.py::get_tree`）：对抽取出的特征词**随机采样 1000 个/步**，直接让 GPT-4 聚类成嵌套 JSON 树，迭代多步存 `all_tree_structures.json`。树的层级结构（粗粒度维度 → 叶子特征）完全是 LLM 归纳的，不是人工定义的。

也就是说，"训练一个分类器/聚类器来归纳特征体系"这件事，被"每次采样后问一遍 LLM"替代了——**归纳能力来自模型预训练知识，不需要在本地语料上训练**。频次统计、top-N 剪枝等后续环节反而是纯静态代码。

## 2. 代价与风险（从代码中直接可见）

| 问题 | 证据 | 影响 |
|---|---|---|
| 成本 | 建树环节 `sample_num=1000, step=1000`，最坏 1000 次 GPT-4 调用只为一个树；抽取环节每文件一次调用 | 按文件逐个抽，语料越大成本线性膨胀 |
| 幻觉 | prompt12 含 `summary/purpose/issues & bugs` 等叙述类，且 EpiCoder 自己统计时要把它们 `skip_features` 剔除 | LLM 产出的特征**无结构真值可验证**，错误会静默进入下游统计 |
| 非确定/不可复现 | `get_tree` 每步 `random.sample` 后独立问 LLM，无温度控制，多步树互不一致 | 特征体系随运行变化，同一语料两次建树结果不同 |
| 解析脆弱 | 手工 `find("<begin>")` + `json.loads`，失败时直接存 `parse_error_str` 字符串 | 无 schema 校验、无重试，靠人工发现 |
| 粒度粗 | 抽的是"语义描述"（如 `base conversion`），不是调用名/实参/类型 | 可用于分类与描述，不能作为检索的精确索引键 |

## 3. 对 libref 的结论：可行，但 LLM 应放在"归纳层"而非"抽取层"

libref 与 EpiCoder 的目标不同：libref 需要的是**可检索、可统计、可复现**的索引（SQLite 为唯一事实源），不是一次性训练数据。因此：

**不该做的**：像 EpiCoder 那样对每个源码文件调 LLM 抽特征。理由：(a) 成本随语料线性增长且不可增量复算（LLM 输出不稳定，重跑结果漂移，破坏 SQLite 单一事实源）；(b) API 调用名、实参、行号这类结构事实用 tree-sitter 抽取是**零幻觉、零成本、可复现**的，LLM 在这里没有任何优势；(c) CodeScholar 的教训同理——它训练 GNN 是为了做"结构级包含判定"这种需要海量判别的任务，这类高频判别也不适合逐条调 LLM。

**可以做的**（LLM 真正占优的场景——归纳、命名、解释）：

1. **模式命名与解释**。`seq_patterns` / 频次共现挖掘产出的是结构化模式（API 序列、共现对），本身没有语义标签。把**聚合成百上千个文件压成的模式**（而非原始代码）交给 LLM 归纳为"惯用工作流"描述——输入量是模式数而非文件数，成本从 O(语料) 降到 O(模式)，且输入是静态事实，幻觉风险仅限于措辞而非事实。
2. **特征体系建树**。借鉴 EpiCoder `get_tree` 的做法，但把输入从"原始语义特征词"换成"静态挖掘出的 API/模式名"，让 LLM 归纳层级维度（数据处理/计算/IO/错误处理……）。采样多步 + 人工或规则合并可对冲非确定性。
3. **检索答案生成**。libref 现有 `llm/` 网关本来就承担 grounded answer；上述 1、2 的产物直接作为 RAG 语料喂给它即可，无需新出口。

**工程约束**（吸收 EpiCoder 的教训）：输出用 JSON Schema/pydantic 强校验（替代 `<begin>/<end>` 手工解析）；温度取 0 并缓存确定性产物；批量任务走断点续跑 + 幂等键（模式哈希）；LLM 产物单独存表、可整体重建，不与静态事实混存。

## 4. 三路线对比

| 维度 | 训练模型（CodeScholar GNN） | 纯 LLM 归纳（EpiCoder） | 静态挖掘 + LLM 归纳（建议） |
|---|---|---|---|
| 结构事实（调用/实参/序列） | 精确但需训练+GPU | 幻觉风险高 | **tree-sitter，零幻觉** |
| 语义归纳（命名/分类/描述） | 无 | **强** | **LLM 在聚合后的模式上做** |
| 成本 | 一次性训练贵，推理快 | 随语料线性膨胀 | LLM 只作用于模式集合，接近常数级 |
| 可复现性 | 高（权重固定） | 低（输出漂移） | 高（静态事实固定，LLM 产物可重建） |
| 验证手段 | 子图同构对照 | 无 | 静态事实可验证；LLM 产物走 RAG 评测基线 |

## 5. 结论

**可以用 LLM 直接归纳特征、代替训练模型，但仅限于"归纳"环节**：EpiCoder 实证了 LLM 的预训练知识足以在不训练、不微调的情况下归纳出层级特征体系；而结构事实的抽取与高频判别仍应留给 tree-sitter 静态挖掘。对 libref 的落点是把 LLM 从"逐文件抽取器"改位为"模式层归纳器"——对 `seq_patterns` 与频次统计的产物做命名、分类树归纳与惯用工作流描述，产物经 pydantic 校验后入库，供检索与 grounded answer 消费。这样既拿到 LLM 归纳能力，又保住 SQLite 单一事实源的可复现性。
